# 자동 테스트와 실패 재현 전략

## 1. 왜 실패를 직접 만들었는가

DB FleetOps는 백업처럼 오래 걸리는 운영 작업을 다룹니다. 정상적인 요청만 확인해서는 실제 운영 상황에서 `OperationJob`과 `OperationTask` 상태를 신뢰할 수 있는지 알기 어렵습니다.

다음 상황은 코드로만 예상하지 않고 실제 Process와 Network 경계에서 재현했습니다.

- 현장 실행기가 오랫동안 백업하는 사이에도 중앙 관제 서버는 계속 응답하는가
- 작업 중인 현장 실행기가 예고 없이 종료되어도 Task가 유실되지 않는가
- 두 Poll이 동시에 도착해도 하나의 Task는 한 번만 선점되는가
- 완료 결과를 저장한 뒤 응답만 유실되어도 후속 Task가 중복 생성되지 않는가

핵심은 “장애가 발생하지 않는가”가 아닙니다. 장애가 발생한 뒤에도 작업 장부와 후속 처리 결과를 계속 신뢰할 수 있는지 확인하는 것입니다.

## 2. 어떤 환경에서 확인했는가

Mock만으로는 Process 종료, DB Lock 경합, HTTP 응답 유실을 그대로 확인하기 어렵습니다. `failureTest`는 Testcontainers로 실제 실행 경계를 만듭니다.

```text
JUnit 실험
  ├─ Metadata MySQL
  ├─ 실제 Spring Boot JAR로 실행한 중앙 관제 서버
  ├─ 실제 Go 실행 파일로 실행한 현장 실행기
  └─ HTTP 장애를 만드는 Toxiproxy
```

`TestEnvironment`는 Container 시작과 정리, Agent 등록, Task 생성, API 호출과 Metadata DB 조회를 담당합니다. 각 실험은 환경 코드를 반복하지 않고 다음 흐름에만 집중합니다.

```text
확인할 주장과 통과 기준을 먼저 정합니다
  → 실제 장애를 만듭니다
  → API와 작업 장부의 변화를 관찰합니다
  → 통과 여부와 실험의 한계를 함께 남깁니다
```

운영 기본값을 그대로 기다리지 않도록 실험에서는 Task Lease를 6초, Lease 갱신을 2초, 만료 검사를 1초로 줄입니다. 시간만 줄였을 뿐, 실제 Poll·Lease·상태 변경 코드를 그대로 실행합니다.

## 3. 긴 현장 작업 중에도 중앙 관제 서버는 응답하는가

### 왜 확인했는가

백업은 수초에서 수시간까지 걸릴 수 있습니다. 이 작업이 중앙 관제 서버의 요청 처리와 묶이면 상태 조회나 다른 운영 요청까지 느려질 수 있습니다.

### 어떻게 만들었는가

실제 Go Agent는 실행하되, 실험용 `mysqldump`가 20초 동안 실행되도록 했습니다. Task가 `RUNNING`인 동안 500ms마다 중앙 관제 서버의 상태 API를 호출했습니다.

```text
20초 백업 Task 시작
  → Task RUNNING 확인
  → 500ms마다 중앙 상태 API 호출
  → 성공률과 각 응답 시간 기록
  → Task SUCCEEDED 확인
```

통과 기준은 상태 API 성공률 100%, 모든 응답 2초 미만입니다. 관찰된 37회의 호출은 모두 성공했고 가장 느린 응답은 15ms였습니다.

### 이 결과가 뜻하는 것

긴 작업을 Agent Process가 실행하는 동안에도 중앙 관제 서버는 다른 요청을 처리했습니다. 다만 가짜 `mysqldump`는 실행 시간만 재현합니다. 실제 대용량 백업의 CPU·Disk I/O 부하는 별도 환경에서 측정해야 합니다.

## 4. 현장 실행기가 죽으면 Task는 어떻게 되는가

### 왜 확인했는가

Agent가 Task를 선점한 직후 종료되면 완료 결과를 보고할 수 없습니다. 별도의 복구 규칙이 없으면 Task는 실제로 실행되지 않으면서 `RUNNING`으로 남을 수 있습니다.

### 어떻게 장애를 만들었는가

30초가 걸리는 백업 Task를 선점한 Agent Container에 `SIGKILL`을 보냈습니다. 정상 종료 과정을 거치지 않으므로 Heartbeat와 Task Lease 갱신이 즉시 멈쵥니다.

```text
Agent가 Task 선점
  → Task RUNNING
  → Agent Process에 SIGKILL
  → Lease 갱신 중단
  → Lease 만료
  → 같은 Task ID를 QUEUED로 복구
  → 같은 자격의 Agent 재시작
  → 실행 번호를 높여 다시 선점
  → Task SUCCEEDED
```

Agent를 재시작했다고 기존 Lease를 이어받는 것은 아닙니다. 만료 검사가 Task를 `QUEUED`로 돌려놓으면, 재시작한 Agent가 다음 Task를 Poll하고 새 실행 번호로 다시 선점합니다.

### 이 결과가 뜻하는 것

Agent Process가 강제 종료되어도 Task 장부는 사라지지 않고 다시 실행할 수 있는 상태로 복구됐습니다. 같은 Task ID를 유지하므로 운영자가 하나의 작업 이력을 계속 추적할 수 있습니다.

현재 백업은 중단된 지점부터 이어서 수행하지 않고 처음부터 다시 실행합니다. 또한 이 실험은 다른 Agent로의 자동 재배정이 아니라 같은 Agent ID와 Token으로 재시작한 경우를 확인했습니다.

## 5. 두 Poll이 동시에 도착하면 누가 Task를 가져가는가

### 왜 확인했는가

Task 조회와 선점이 따로 처리되면 두 Poll이 같은 `QUEUED` Task를 읽은 뒤 각각 실행할 수 있습니다. 백업이 두 번 실행되면 파일과 후속 Task까지 중복될 수 있습니다.

### 어떻게 경합을 만들었는가

하나의 `QUEUED` Task를 준비한 뒤 두 가상 Thread를 같은 Barrier에서 출발시켰습니다. 두 Thread는 같은 Agent의 `POST /tasks/next`를 거의 동시에 호출합니다.

서버는 하나의 Transaction 안에서 다음 순서를 처리합니다.

```text
가장 오래 대기한 QUEUED Task 조회
  → Task 행에 비관적 쓰기 Lock
  → RUNNING으로 변경
  → 실행 번호 증가와 Lease 설정
  → 선점한 Task 반환
```

첫 번째 Poll이 행 Lock을 얻으면 두 번째 Poll은 기다립니다. 첫 Transaction이 Task를 `RUNNING`으로 바꾸고 끝나면, 두 번째 Poll은 더 이상 가져갈 `QUEUED` Task를 찾지 못합니다.

### 이 결과가 뜻하는 것

두 Poll이 동시에 하나의 대기 Task를 요청해도 같은 Task가 두 응답에 함께 반환되지 않았습니다.

현재 실험은 Task 하나를 생성한 뒤 Poll 두 개를 20회 호출합니다. 실제 `QUEUED` Task를 두고 경합하는 핵심 상황은 첫 회에 발생하고, 나머지 호출은 이미 `RUNNING`인 Task가 다시 반환되지 않는지 확인합니다. 20번의 독립적인 경합을 증명하려면 회차마다 새 `QUEUED` Task를 만드는 보완이 필요합니다.

## 6. 완료 결과는 저장됐지만 HTTP 응답만 사라지면 어떻게 되는가

### 왜 확인했는가

Agent가 완료 요청의 응답을 받지 못했다고 해서 서버가 요청을 처리하지 않은 것은 아닙니다. 서버는 이미 Task를 성공으로 저장하고 복원 검증 Task까지 만들었을 수 있습니다. 이때 같은 결과를 다시 처리하면 후속 Task가 중복 생성됩니다.

### 어떻게 응답만 유실시켰는가

Agent와 중앙 관제 서버 사이에 Toxiproxy를 두고 서버에서 Agent로 돌아가는 응답 방향에 Timeout을 설정했습니다.

```text
Agent
  → 고정된 실행 번호·결과 보고 ID·결과로 완료 요청
  → 중앙 관제 서버가 Task 성공과 복원 검증 Task를 Commit
  → Toxiproxy가 Agent로 돌아가는 HTTP 응답만 유실
  → 같은 실행 번호·결과 보고 ID·결과를 재전송
```

중앙 관제 서버는 첫 보고에서 Task에 다음 값을 남깁니다.

- 현재 실행 번호
- Agent가 만든 결과 보고 ID
- 성공 또는 실패라는 결과 종류
- 결과 내용으로 만든 SHA-256 지문

재전송된 값이 모두 같으면 이미 접수한 결과로 판단하고 기존 Task를 HTTP 200으로 반환합니다. 하나라도 다르면 이전 실행의 결과나 변경된 보고로 보고 HTTP 409로 거절합니다.

실험에서는 동일한 완료 결과를 재전송했을 때 HTTP 200을 받았고, `MYSQL_RESTORE_VERIFY` Task가 정확히 하나만 있는지 확인했습니다.

### 이 결과가 뜻하는 것

같은 결과 보고는 여러 번 도착해도 Task 상태 변경과 후속 처리가 한 번만 수행됩니다.

다만 현재 Go Agent는 완료 결과를 파일에 보관했다가 재시작 후 자동으로 재전송하지 않습니다. 이 실험은 같은 결과를 직접 다시 보내 중앙 관제 서버의 중복 보고 처리를 검증합니다. Agent Outbox와 재시작 후 자동 재전송은 후속 보완 범위입니다.

## 7. 실험 코드를 어떻게 나누었는가

디렉터리는 실험 환경, 장애 시나리오, 구조의 타당성을 확인하는 실험으로만 나눅니다.

```text
failure/
  ├─ environment/  Container·HTTP·DB 공통 환경
  ├─ scenario/     장애를 직접 만드는 시나리오
  └─ validity/     Control Plane–Agent 분리 구조의 효과 측정
```

`TestEnvironment`는 실험 장비를 준비합니다. `AgentFailureTest`는 `SIGKILL`, 동시 Poll, 응답 유실처럼 장애를 만들고 결과를 검증합니다. `ArchitectureTest`의 각 Check는 확인할 주장, 통과 기준, 관찰값과 한계를 같이 보여줍니다.

복잡한 결과 파일은 만들지 않습니다. JUnit의 성공·실패와 Console에 출력한 관찰값으로 바로 판단합니다.

## 8. 실행 방법

Docker를 사용할 수 없을 때 실험이 조용히 건너뛰지 않도록 `FAILURE_TEST_REQUIRE_DOCKER=true`를 지정합니다.

```bash
# Agent 종료·동시 Poll·응답 유실
FAILURE_TEST_REQUIRE_DOCKER=true \
./gradlew agentFailureTest --rerun-tasks --console=plain

# 긴 작업 응답성과 Process 분리 구조
FAILURE_TEST_REQUIRE_DOCKER=true \
./gradlew architectureTest --rerun-tasks --console=plain
```

## 9. 아직 증명하지 않은 것

- 실제 대용량 백업의 CPU·Memory·Disk I/O 부하는 재현하지 않았습니다.
- 중단된 백업을 중간 지점부터 이어서 실행하지 않습니다.
- Task를 다른 Agent로 자동 재배정하는 실패 복구는 확인하지 않았습니다.
- 동시 Poll을 20번의 독립적인 Task 경합으로 재현하려면 실험 보완이 필요합니다.
- Agent가 완료 결과를 디스크에 보존하고 재시작 후 자동 재전송하는 기능은 아직 없습니다.
- Metadata DB 복제·백업·재해 복구 능력은 이 실험의 범위가 아닙니다.
