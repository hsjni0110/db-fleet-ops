# 자동 테스트와 실패 재현 전략

## 1. 테스트를 나눈 기준

테스트는 빠르게 확인할 코드와 실제 환경이 필요한 검증을 분리합니다.

| 종류 | 확인하는 내용 | 기본 실행 여부 |
|---|---|---|
| 단위 테스트 | 도메인 규칙, Service 판단, Handler 동작 | `test`에 포함 |
| MVC 테스트 | HTTP 상태, Validation과 공통 오류 응답 | `test`에 포함 |
| 통합 테스트 | 실제 MySQL 연결이 필요한 흐름 | 별도 실행 |
| 실패 재현 테스트 | Agent 종료, 동시 요청과 응답 유실 | 별도 실행 |
| 구조 타당성 테스트 | Control Plane과 Agent 분리의 효과 | 별도 실행 |

일반 테스트는 외부 인프라 없이 빠르게 실행되어야 합니다. Docker나 실제 MySQL이 필요한 검증은 별도 Gradle Task로 실행합니다.

## 2. 단위 테스트

Service 테스트에서는 Repository나 외부 Probe를 Mock으로 바꾸고 Service의 판단만 확인합니다. 도메인 테스트는 상태 변경 규칙을 객체에 직접 적용합니다.

예를 들어 Task Lease 테스트는 고정된 시각을 사용해 다음 경계를 확인합니다.

- 선점하면 실행 번호와 Lease가 설정되는가
- Lease 만료 시 Task가 다시 대기하는가
- 이전 실행 번호의 결과를 거절하는가
- 최대 시도 횟수에 도달하면 `TIMED_OUT`이 되는가

시간을 고정하면 테스트 실행 속도와 관계없이 같은 결과를 얻을 수 있습니다.

## 3. MVC 테스트

전역 예외와 요청 Validation은 실제 Spring MVC 흐름을 사용하는 `MockMvc`로 확인합니다.

- HTTP 상태 코드
- `application/problem+json`
- 안정된 `errorCode`
- `requestId`
- 필수 필드와 UUID 형식 오류
- 지원하지 않는 HTTP Method

문구 전체보다 API 계약에 해당하는 필드를 중심으로 검증합니다.

## 4. 통합 테스트

실제 MySQL이 필요한 테스트에는 다음 Tag를 사용합니다.

```java
@Tag("integration")
```

```bash
./gradlew test
./gradlew integrationTest
```

`integrationTest`를 기본 `check`에 연결하지 않았습니다. Docker나 Database가 없는 환경에서도 빠른 코드 검증은 수행할 수 있어야 하기 때문입니다.

외부 MySQL을 사용하는 테스트는 다음 환경변수를 사용합니다.

```text
DB_TARGET_HOST
DB_TARGET_PORT
DB_TARGET_NAME
DB_TARGET_USERNAME
DB_TARGET_PASSWORD
```

## 5. Control Plane–Agent 테스트 환경

Control Plane과 Go Agent 사이의 장애는 Mock만으로 확인하기 어렵습니다. `failureTest` Source Set은 Testcontainers로 실제 Process와 Network 경계를 만듭니다.

```text
JUnit
  ├─ Metadata MySQL Container
  ├─ Control Plane Container
  ├─ Go Agent Container
  └─ Toxiproxy Container
```

공통 환경은 `TestEnvironment`가 담당합니다.

- Container 시작과 종료
- Agent 등록과 실행
- Task 생성과 상태 조회
- Control Plane HTTP 요청
- Metadata DB 조회
- Toxiproxy 시작

개별 테스트는 환경 구현을 반복하지 않고 “무슨 장애를 만들고 무엇을 확인하는가”만 표현합니다.

## 6. 실패 재현 테스트

실패 재현 테스트는 다음 명령으로 실행합니다.

```bash
FAILURE_TEST_REQUIRE_DOCKER=true \
./gradlew agentFailureTest --rerun-tasks --console=plain
```

현재 확인하는 시나리오는 네 가지입니다.

### 6.1 긴 Backup 중 Heartbeat

20초 동안 실행되는 가짜 `mysqldump` 중에도 Heartbeat가 계속 저장되고 Task가 성공하는지 확인합니다.

### 6.2 Agent 강제 종료 뒤 Task 회수

실행 중인 Agent Container에 `SIGKILL`을 보내고 Lease가 만료된 Task가 `QUEUED` 또는 `TIMED_OUT`으로 정리되는지 확인합니다.

### 6.3 동시 Poll의 중복 선점

같은 Agent가 동시에 두 번 Poll하도록 만들고 하나의 Task가 두 요청에 함께 반환되지 않는지 20회 확인합니다.

### 6.4 완료 응답 유실

Toxiproxy로 완료 응답만 유실시킨 뒤 동일한 결과를 다시 전송합니다. 재전송이 HTTP 200을 받고 복원 확인 Task가 한 번만 생성되는지 확인합니다.

각 테스트는 다음처럼 단순한 구조를 유지합니다.

```text
환경 준비
  → 장애 주입
  → API와 DB 상태 확인
  → JUnit assertion
  → 임시 Container 정리
```

실패 여부는 JUnit 결과와 콘솔 관찰값으로 확인합니다. 테스트가 별도의 `docs/evidence` 파일이나 결과 DTO를 생성하지는 않습니다.

## 7. 구조 타당성 테스트

분리 구조가 의도한 효과를 내는지는 다음 명령으로 확인합니다.

```bash
FAILURE_TEST_REQUIRE_DOCKER=true \
./gradlew architectureTest --rerun-tasks --console=plain
```

이 테스트는 다음 내용을 측정합니다.

- 긴 Agent 작업 중에도 Control Plane API가 응답하는가
- Agent가 외부 수신 Port 없이 작업하는가
- 한 Agent의 장애가 다른 Agent로 전파되지 않는가
- Control Plane 재시작 뒤 Task 장부가 남는가
- Go Agent의 파일 크기, Memory, 시작 시간과 다중 Architecture Build가 기준을 만족하는가

측정값과 판정은 테스트 콘솔에서 바로 확인합니다. 별도 결과 파일은 생성하지 않습니다.

## 8. failureTest 코드 구조

테스트 코드는 역할별 디렉터리와 같은 Java Package로 구분합니다.

```text
failure/
  ├─ environment/   `com.dbfleetops.failure.environment`
  ├─ scenario/      `com.dbfleetops.failure.scenario`
  └─ validity/      `com.dbfleetops.failure.validity`
```

복잡한 Report Model이나 Timeline Model은 두지 않습니다. 테스트에서 필요한 상태는 해당 테스트 안의 지역 변수로 유지하고 바로 assertion합니다.

## 9. 현재 테스트의 한계

- 가짜 `mysqldump`의 대기 시간은 재현하지만 실제 대용량 Backup의 CPU와 Disk 부하는 재현하지 않습니다.
- Docker Port 공개 여부는 확인하지만 실제 회사 방화벽 정책까지 검증하지 않습니다.
- Testcontainers 환경의 단일 Metadata MySQL을 사용하므로 DB 복제와 재해 복구 능력은 확인하지 않습니다.
- Agent Container 종료는 재현하지만 Host 전체 장애, Network Partition과 장시간 불안정은 더 많은 시나리오가 필요합니다.
- 구조 타당성 수치는 개발 장비와 Container Runtime에 따라 달라질 수 있습니다.

CI에서는 빠른 `test`, 외부 MySQL `integrationTest`, Docker 기반 `agentFailureTest`와 `architectureTest`를 별도 단계로 실행하는 것이 적절합니다.
