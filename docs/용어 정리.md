# DB FleetOps 용어 정리

## 1. 문서 규칙

이 문서는 DB FleetOps의 코드, API, UI, 테스트, 설계 문서에서 사용할 공통 언어를 정의한다.

공통 언어(Ubiquitous Language)는 개발자와 DB 운영자, 기획자가 같은 개념을 같은 이름과 의미로 말하기 위한 약속이다. 이 문서는 특정 기술을 아는 것을 전제하지 않는다.

- 한 개념에는 하나의 기본 용어를 사용한다.
- 코드 이름은 영문, 사용자 문서는 한국어 표현을 기본으로 하되 처음에 영문명을 병기한다.
- `idempotencyKey`, `leaseExpiresAt` 같은 필드 이름은 코드 식별자일 뿐, 문서에서 그대로 사용할
  공통 언어가 아니다. 문서에서는 각각 `중복 방지 값`, `Task 실행권 만료 시각`으로 표현한다.
- 동의어는 새 코드와 문서에서 사용하지 않고 기존 호환성을 위한 경우에만 남긴다.
- 상태명은 단순 번역보다 해당 aggregate에서의 의미를 우선한다.

### 1.1 먼저 알아둘 기본 표현

| 표현 | 쉽게 설명한 의미 | 예시 |
|---|---|---|
| Database(DB) | 업무 데이터를 구조화해 저장하고 조회하는 공간 | 주문 DB, 회원 DB |
| DBMS | DB를 만들고 운영하는 software 종류 | MySQL, PostgreSQL |
| DB Instance | 특정 server에서 실제로 실행 중인 DBMS 하나 | `db-prod-01:3306`의 MySQL |
| Host | DBMS나 Agent가 실행되는 server 또는 가상 server | `db-prod-01` |
| Parameter | DBMS의 동작 방식을 조절하는 설정 항목 | `max_connections` |
| API | 다른 프로그램이 FleetOps에 요청하고 결과를 받는 규칙과 통로 | DB 목록 조회 API |
| Console | 운영자가 browser에서 FleetOps를 사용하는 화면 | DB 목록, Job 상세 화면 |
| JSON | 프로그램 간에 이름과 값으로 구조화된 정보를 주고받는 형식 | `{"databaseId": 1}` |
| ID(식별자) | 이름이 같아도 각 대상을 구분하는 고유한 값 | `databaseId=42` |
| 상태 | 대상이 현재 어떤 단계에 있는지를 나타내는 값 | 대기, 실행 중, 성공, 실패 |
| 상태 전이 | 운영 행위에 따라 한 상태에서 다른 상태로 바뀌는 것 | `QUEUED -> RUNNING` |
| 생명주기 | 대상이 생성되고 상태가 바뀌며 종료되는 전체 과정 | Job 생성부터 성공·실패까지 |
| Metric | 시스템 상태를 숫자로 관찰하기 위한 측정값 | CPU 사용률, Job 실패 수 |
| Log | 시스템에서 발생한 일을 시각과 함께 남긴 기록 | DB 연결 실패 기록 |
| Heartbeat | Agent가 정상적으로 실행 중임을 주기적으로 알리는 신호 | “나는 현재 온라인이다”라는 Agent 보고 |
| Uptime | DBMS 또는 system이 마지막으로 시작된 후 중단 없이 운영된 시간 | 36시간 |
| Transaction | 여러 DB 변경을 하나의 업무 단위로 처리하는 묶음 | 주문 생성과 재고 감소 |
| Lock Wait | 다른 transaction이 사용 중인 데이터를 변경하기 위해 기다리는 상태 | 주문 A 수정이 끝나기를 주문 B 수정이 대기 |
| Slow Query | 기준보다 오래 걸리거나 많은 데이터를 검사하는 SQL | 평균 10초가 걸리는 조회 |
| 논리 백업 | table 구조와 데이터를 SQL 등 논리적 형태로 저장한 백업 | `mysqldump` 파일 |
| 임시 자원 정리 | 임시로 만든 자원을 실행 후에 제거하는 행위 | 복원 검증용 임시 DB 제거 |

### 1.2 Job과 Task를 구분하는 법

“production DB를 백업하고 복원 가능한지 확인해 달라”는 하나의 **Job**이다. 이 Job을 완료하기 위해 Agent가 수행하는 “MySQL backup 파일 생성”과 “임시 DB에 복원하여 검증”은 각각의 **Task**다.

- Job: 사용자가 달성하려는 운영 목표.
- Task: 해당 목표를 위해 system이 실행하는 구체적인 일.

한국어 문서에서는 처음에 **운영 Job(`OperationJob`)**, **운영 Task(`OperationTask`)**로
표기하고, 같은 문맥 안에서는 Job과 Task로 줄여 쓴다. Job을 작업, Task도 작업이라고 부르면
둘을 구분할 수 없으므로 `작업`을 개체 이름으로 단독 사용하지 않는다.

| 표준 용어 | 코드 | 정의 | 피할 표현 |
|---|---|---|---|
| DB FleetOps | `DB FleetOps` | 관리 DB의 상태와 운영 작업을 중앙 관리하는 플랫폼 | Fleet, 모니터링 툴로만 축약 |
| Control Plane | `control plane` | 메타데이터·정책·Job을 관리하는 Java 시스템 | Server, Master |
| Console | `console` | Control Plane API를 사용하는 운영자 UI | Admin이라는 모호한 표현 |
| Agent | `Agent` | DB host 근처에서 허용된 Task를 실행하는 프로세스이자 등록된 실행 주체 | Worker. Worker는 Control Plane Job consumer에만 사용 |
| Agent 인증 토큰 | `agentToken` | 요청을 보낸 프로그램이 등록된 Agent인지 확인하는 비밀값 | DB 접속 인증 정보 |
| Worker | `Worker` | 실행 가능한 Operation Job을 가져가고, 작업 순서와 상태를 조정하는 Control Plane 구성 요소 | Agent |
| 관리 DB | `ManagedDatabase` | FleetOps Inventory에 등록된 DB 인스턴스 | Target DB, Database Inventory Item을 개체명으로 사용 |
| Metadata DB | metadata database | FleetOps 자체의 Entity와 이력을 저장하는 DB | Target DB |
| DBMS 종류 | `DatabaseEngine` | MySQL, PostgreSQL처럼 관리 DB를 실행하는 제품 종류 | databaseType, engineType의 무분별한 혼용 |
| DB 접속 인증 정보 | `DatabaseCredential` | 관리 DB에 로그인할 때 사용하는 계정명과 암호화된 비밀번호 | 접속 정보. host와 port는 인증 정보가 아님 |
| 활성 상태 | `DatabaseStatus` | 관리 DB가 FleetOps 작업 대상인지를 나타내는 `ACTIVE|INACTIVE` | Health Status |
| 건강 상태 | `HealthStatus` | 점검 결과로 판단한 `HEALTHY|DEGRADED|CRITICAL|UNKNOWN` | 활성 상태 |
| 연결 상태 | health check result | 한 번의 연결 점검 결과인 `UP|DOWN` | 건강 상태와 동의어로 사용 |
| 연결 점검 | health check | DB에 연결할 수 있는지와 응답 시간을 확인하는 점검 | 운영 진단 |
| 운영 진단 | diagnostics | 버전·세션·트랜잭션 등 DB 운영 상태를 조회하는 진단 | 연결 점검 |

## 3. 운영 작업 용어

| 표준 용어 | 코드 | 정의 | 피하거나 구분할 표현 |
|---|---|---|---|
| 운영 Job | `OperationJob` | 사용자가 달성하려는 하나의 운영 목표와 전체 상태·결과 | Task, 단독 표현인 작업 |
| 운영 Task | `OperationTask` | Agent가 한 번의 실행으로 수행하는 구체적인 단위 | Job, 단독 표현인 작업 |
| Job 종류 | `JobType` | 백업·설정 점검·설정 적용 같은 운영 목적의 분류 | Task 종류 |
| Task 종류 | `OperationTaskType` | Linux 상태 수집·MySQL 논리 백업·MySQL 복원 검증 같은 Agent 실행 계약 | Job 종류 |
| Job 가져오기 | `OperationJob.start` | Worker가 실행 가능한 Job 하나와 Job 실행권을 얻는 행위 | Task 가져오기, Task 확인 요청 |
| Task 확인 요청 | `nextTask` | Agent가 자신의 다음 Task가 있는지 Control Plane에 묻는 행위 | Task를 실제로 가져온 결과 |
| Task 가져오기 | `OperationTask.claim` | Task 확인 요청의 결과로 Agent가 대기 중인 Task 하나와 Task 실행권을 얻는 행위 | Job 가져오기 |
| Job 실행권 | `leaseOwner`, `leaseUntil` | 특정 Worker만 정해진 시각까지 Job을 처리할 수 있는 권한 | Task 실행권, DB 잠금 |
| Task 실행권 | `leaseExpiresAt` | 특정 실행 번호의 Agent만 정해진 시각까지 Task를 처리할 수 있는 권한 | Job 실행권, DB 잠금 |
| 실행 번호 | `executionAttempt` | Task를 가져올 때마다 증가하며 이전 실행과 현재 실행을 구분하는 번호 | Job의 재시도 횟수 |
| 재대기 | `requeue` | 같은 Job 또는 Task를 새로 만들지 않고 상태를 다시 `QUEUED`로 바꾸는 행위 | 재시도, 새 개체 생성 |
| 재시도 | `retry` | 재대기된 같은 Job이나 Task를 다시 가져와 실행하는 것 | 재대기라는 상태 변경 자체 |
| 실행권 만료 처리 | lease recovery | 실행권이 만료된 Job·Task의 상태를 확인하고 실행권 연장, 재대기 또는 시간 초과를 결정하는 과정 | 단순 삭제, 새 Job·Task 생성 |
| 중복 방지 값 | `idempotencyKey` | 같은 운영 Job이 두 번 만들어지는 것을 막기 위해 요청자가 제공하는 값 | Job ID, 결과 보고 번호 |
| 결과 보고 번호 | `resultReportId` | Agent가 만든 결과를 다시 보낼 때 같은 보고인지 구분하는 UUID | 중복 방지 값, Task ID |
| 결과 확인값 | `resultReportFingerprint` | 결과 종류와 내용으로 계산하여 재전송된 결과가 이전 내용과 같은지 확인하는 값 | 사용자에게 보여 주는 결과 코드 |
| 중복 결과 보고 | `DUPLICATE` | 실행 번호, 결과 보고 번호, 결과 종류와 결과 확인값이 모두 같은 재전송 | 내용이 달라 충돌하는 결과 보고 |
| Job 요청 내용 | `requestPayload` | Job 종류별 요청 조건을 담은 JSON | Task 실행 조건 |
| Task 실행 조건 | `parametersJson` | Agent가 Task를 실행하는 데 필요한 조건을 담은 JSON | Job 요청 내용, DB 접속 인증 정보 원문 |
| Task 결과 내용 | `resultPayloadJson` | Agent가 보고한 구조화된 Task 실행 결과 JSON | Job 결과 메시지 |
| 작업 흐름 | workflow | Task 결과에 따라 다음 Task를 만들거나 Job을 끝내는 순서와 판정 규칙 | Worker, 단순 상태 전이 |
| 진행 중 Task | active task | 상태가 `QUEUED` 또는 `RUNNING`이어서 아직 끝나지 않은 Task | 관리 DB의 활성 상태 |
| 종료 상태 | terminal status | 더 이상 실행하지 않는 `SUCCEEDED`, `FAILED`, `CANCELLED`, `TIMED_OUT` 상태 | `QUEUED`, `RUNNING` |
| 실행 성공 | task execution success | Agent가 Task 명령을 오류 없이 실행하고 결과를 보고한 것 | 복원 검증 통과 |
| 복원 검증 통과 | verified | 백업 산출물을 복원하고 정의된 검증 기준을 충족한 것 | Task 명령의 실행 성공 |

### 3.1 Agent와 Worker를 구분하는 법

Agent와 Worker는 모두 “일을 처리한다”는 점에서 헷갈리기 쉽다. 하지만 위치와 책임이 다르다.

- Worker는 Control Plane 안에서 대기 중인 Job을 고르고 실행 순서를 조정한다. 공장의 작업 관리자에 가깝다.
- Agent는 DB host 근처에서 backup program 실행과 같은 실제 Task를 수행한다. 현장의 작업자에 가깝다.

Job 가져오기와 Job 실행권은 두 Worker가 같은 Job을 동시에 처리하지 않게 한다. Worker A가
Job을 가져오면 실행권이 유효한 동안은 Worker A만 그 Job을 처리할 수 있다. Task도 같은 원리로
Agent가 가져오지만, Job 실행권과 Task 실행권은 서로 다른 권한이다.

Task 확인 요청은 “할 일이 있는지 묻는 것”이고, Task 가져오기는 “Task와 실행권을 받은 결과”다.
따라서 빈 응답은 Task 가져오기가 아니며, Task를 반환받았을 때만 가져오기에 성공한 것이다.

## 4. 설정 정책 용어

| 표준 용어 | 코드 | 정의 | 피할 표현 |
|---|---|---|---|
| DB 설정 | configuration | DBMS의 동작을 조절하는 설정 항목과 값의 집합 | Config라는 축약어 |
| 설정 기준 | `ConfigurationProfile` | DBMS 종류·환경·버전 범위에 맞게 지켜야 할 설정값 묶음 | Policy라는 단독 표현 |
| 설정 기준 항목 | `ConfigurationProfileParameter` | 설정 기준에 포함된 하나의 설정값 규칙 | 실제 설정 항목 |
| 기대 설정 | desired state | 설정 기준에 정의된 바람직한 설정 상태 | 기대 스냅샷 |
| 실제 설정 기록 | `ConfigurationSnapshot` | 특정 시점에 관리 DB에서 수집한 설정값 묶음 | 설정 기준 |
| 실제 설정 | actual state | 관리 DB에서 관찰한 현재 설정 상태 | 현재 Profile |
| 설정 차이 | `ConfigurationDrift` | 기대 설정과 실제 설정을 비교하여 찾은 차이 | 실제 설정 기록 자체 |
| 설정 일치 여부 | `ComplianceStatus` | 실제 설정값이 기대 설정값과 일치하는지에 대한 판정 | 설정 적용 결과 |
| 일치 | `COMPLIANT` | 실제 설정값이 기대 설정값과 같음 | 건강 상태 |
| 불일치 | `NON_COMPLIANT` | 실제 설정값은 있지만 기대 설정값과 다름 | 누락 |
| 누락 | `MISSING` | 필요한 설정 항목을 실제 설정에서 찾을 수 없음 | 불일치 |
| 설정 적용 | `ConfigurationApply` | 허용된 설정 변경을 관리 DB에 적용하고 결과를 확인하는 운영 행위 | 설정 기준 활성화 |
| 실행 중 변경 가능 | `dynamic` | DBMS를 재시작하지 않고 변경할 수 있는 설정 항목 | 적용 허용 |
| FleetOps 적용 허용 | `applyAllowed` | FleetOps가 해당 설정 항목을 직접 변경해도 된다는 정책 | 실행 중 변경 가능 |
| 적용 전·후 설정 기록 | `beforeSnapshotId`, `afterSnapshotId` | 설정 적용 전과 후에 각각 수집한 실제 설정 기록 | 백업 |

### 4.1 설정 점검과 적용 예시

production MySQL의 `max_connections`가 100이고 회사 정책은 200이어야 한다고 가정한다.

- 설정 기준: “production MySQL의 `max_connections`는 200”이라는 기준을 보관한다.
- 실제 설정 기록: DB에서 현재 값 100을 수집한다.
- 설정 차이: 기대값 200과 실제값 100이 다르므로 `NON_COMPLIANT`라고 판정한다.
- 설정 적용: 정책상 변경이 허용된 설정 항목이라면 200으로 변경한다.
- 적용 전·후 설정 기록: 변경 전에 100이었고 변경 후에 200이 되었는지 기록하고 확인한다.

`dynamic=true`라고 해서 FleetOps가 바로 변경할 수 있는 것은 아니다. DBMS가 실행 중 변경을
지원하고, 동시에 운영 정책이 FleetOps의 변경을 허용해야 한다.

## 5. 백업과 복원 검증 용어

| 표준 용어 | 코드 | 정의 | 구분 |
|---|---|---|---|
| 논리 백업 | `MYSQL_LOGICAL_BACKUP` | `mysqldump`처럼 table 구조와 데이터를 논리적인 형식으로 저장하는 백업 | 물리 백업은 현재 범위가 아님 |
| 백업 산출물 | backup file | Agent가 생성한 백업 파일 | 복원 가능성까지 보장하지는 않음 |
| 복원 검증 | `BackupRestoreVerification` | 백업 산출물을 임시 DB에 복원하여 실제로 사용할 수 있는지 확인하는 과정 | 백업 파일 생성 |
| 임시 DB | `temporaryDatabaseName` | 복원 검증을 위해 잠시 만들었다가 제거하는 DB | 원본 관리 DB |
| 임시 DB 정리 | cleanup | 복원 검증 후 임시 DB를 제거하는 행위 | 복원 검증 자체 |
| 검증 통과 | `VERIFIED` | 복원과 table 단위 검증이 성공한 상태 | 임시 DB 정리 성공까지 포함하지 않음 |
| 임시 DB 정리 실패 | `CLEANUP_FAILED` | 복원 또는 검증 후 임시 DB 제거에 실패한 상태 | 복원 검증 실패 |

## 6. 상태 용어

### 6.1 Agent

| 상태 | 의미 |
|---|---|
| `ONLINE` | 등록 또는 최근 heartbeat로 사용 가능하다고 판단 |
| `OFFLINE` | heartbeat 기준을 넘겨 일시적으로 사용 불가 |
| `UNKNOWN` | 현재 상태를 판단할 정보가 부족 |
| `DISABLED` | 관리자가 사용을 금지 |

### 6.2 Job과 Task

| 상태 | 의미 |
|---|---|
| `QUEUED` | 실행 대기 중 |
| `RUNNING` | Worker 또는 Agent가 실행 중 |
| `SUCCEEDED` | 정의된 성공 기준을 충족하고 종료 |
| `FAILED` | 실행이 실패해 종료. Job은 재시도 가능할 수 있음 |
| `CANCELLED` | 명시적 취소로 종료 |
| `TIMED_OUT` | 정해진 횟수 안에 실행을 끝내지 못하거나 만료된 실행권을 회복하지 못해 종료 |

### 6.3 Configuration Apply Item

| 상태 | 의미 |
|---|---|
| `PENDING` | 적용 전 |
| `APPLIED` | DB에 변경 명령을 적용했으나 결과값은 미검증 |
| `VERIFIED` | 적용 후 값이 요청값과 일치 |
| `SKIPPED` | 정책상 실행하지 않음 |
| `UNSUPPORTED` | 현재 DBMS/Adapter가 적용을 지원하지 않음 |
| `FAILED` | 적용 또는 검증 중 실패 |

## 7. 현재 불일치와 정리 후보

| 현재 표현 | 문제 | 정리 후보 |
|---|---|---|
| `ManagedDatabase`, Database Instance, Target DB, Inventory DB | 같은 대상을 여러 이름으로 표현 | 도메인은 `ManagedDatabase`, 문서는 `관리 DB` |
| `database.DatabaseStatus` | Health 상태로 오인 가능 | `ManagedDatabaseStatus` 검토 |
| `health.DatabaseStatus` | 다른 패키지의 동명 enum | `ConnectivityStatus` 또는 기본 흐름 제거 검토 |
| `DatabaseEngine`, `ConfigurationEngineType` | 같은 DBMS 분류를 중복 표현 | 공유 value 또는 명시적 mapper 선택 |
| `databaseType`, `engine`, `engineType` | API·도메인별 필드명 불일치 | 새 계약은 `engine` 우선 |
| AgentTask | 이전 설계명이 문서에 남음 | `OperationTask` |
| Restore Verify, Restore Verification, 복원 확인 | 같은 개념을 여러 이름으로 표현 | 문서에서는 `복원 검증`, 코드의 Task 종류는 `MYSQL_RESTORE_VERIFY` |
| Apply Status | 설정 적용 전체와 항목의 상태가 모호 | 문서는 `설정 적용 상태`, `설정 적용 항목 상태`로 구분하고 코드에서는 전체 enum 이름 사용 |
| Profile status `ACTIVE` | DB의 `ACTIVE`와 의미가 다름 | 항상 `Profile Status`로 문맥 명시 |

## 8. 명명 규칙

- Entity: 식별성과 생명주기가 있는 명사 (`OperationJob`).
- Value Object: 값 자체가 의미이며 불변인 명사 (`ConnectionSummary`).
- 명령/요청 DTO: 사용자 의도를 나타내는 동사+Request/Command (`CreateBackupJobRequest`).
- 조회 응답 DTO: 대상+Response (`OperationJobResponse`).
- 도메인 행위: 기술적 setter보다 용어집의 동사 (`start`, `retry`, `deactivate`, `markVerified`).
- boolean: 질문으로 읽히는 이름 (`isActive`, `tokenMatches`).
- 시각: 이벤트 발생 시점은 `-edAt` (`createdAt`, `completedAt`)을 사용한다. 실행권 만료
  시각은 현재 코드에 `leaseUntil`과 `leaseExpiresAt`이 함께 있으므로 하나로 통일하기 전까지
  새 이름을 임의로 추가하지 않는다.
- ID 참조: 대상명+`Id` (`operationJobId`). `targetDatabaseId`/`databaseId`의 통일은 Job 리팩토링 때 결정한다.

## 9. 미확정 용어

다음은 코드 변경 전에 팀 합의가 필요하다.

- `Inventory`를 목록/컨텍스트명으로 계속 사용할지.
- 연결 상태 `UP|DOWN`과 건강 상태 4단계를 모두 유지할지.
- 부분 성공 Apply/Job의 상위 성공 판정 용어.
- 논리 백업, 복원 검증, 임시 DB 정리의 성공 경계와 최종 사용자 표시 문구.
