# DB FleetOps 용어 정리

## 1. 문서 규칙

이 문서는 DB FleetOps의 코드, API, UI, 테스트, 설계 문서에서 사용할 Ubiquitous Language를 정의한다.

Ubiquitous Language(공통 용어)는 개발자와 DB 운영자, 기획자가 같은 개념을 같은 이름과 의미로 말하기 위한 약속이다. 이 문서는 특정 기술을 아는 것을 전제하지 않는다.

- 한 개념에는 하나의 기본 용어를 사용한다.
- 코드 이름은 영문, 사용자 문서는 한국어 표현을 기본으로 하되 처음에 영문명을 병기한다.
- 동의어는 새 코드와 문서에서 사용하지 않고 기존 호환성을 위한 경우에만 남긴다.
- 상태명은 단순 번역보다 해당 aggregate에서의 의미를 우선한다.

### 1.1 먼저 알아둘 기본 표현

| 표현 | 쉽게 설명한 의미 | 예시 |
|---|---|---|
| Database(DB) | 업무 데이터를 구조화해 저장하고 조회하는 공간 | 주문 DB, 회원 DB |
| DBMS | DB를 만들고 운영하는 software 종류 | MySQL, PostgreSQL |
| DB Instance | 특정 server에서 실제로 실행 중인 DBMS 하나 | `db-prod-01:3306`의 MySQL |
| Host | DBMS나 Agent가 실행되는 server 또는 가상 server | `db-prod-01` |
| Parameter | DBMS의 동작 방식을 조절하는 설정 항목 | `max_connections` |
| API | 다른 프로그램이 FleetOps에 요청하고 결과를 받는 규칙과 통로 | DB 목록 조회 API |
| Console | 운영자가 browser에서 FleetOps를 사용하는 화면 | DB 목록, Job 상세 화면 |
| JSON | 프로그램 간에 이름과 값으로 구조화된 정보를 주고받는 형식 | `{"databaseId": 1}` |
| ID(식별자) | 이름이 같아도 각 대상을 구분하는 고유한 값 | `databaseId=42` |
| 상태 | 대상이 현재 어떤 단계에 있는지를 나타내는 값 | 대기, 실행 중, 성공, 실패 |
| 상태 전이 | 운영 행위에 따라 한 상태에서 다른 상태로 바뀌는 것 | `QUEUED -> RUNNING` |
| Lifecycle | 대상이 생성되고 변경되며 종료되는 전체 과정 | Job 생성부터 성공·실패까지 |
| Metric | 시스템 상태를 숫자로 관찰하기 위한 측정값 | CPU 사용률, Job 실패 수 |
| Log | 시스템에서 발생한 일을 시각과 함께 남긴 기록 | DB 연결 실패 기록 |
| Heartbeat | Agent가 정상적으로 실행 중임을 주기적으로 알리는 신호 | “나는 현재 온라인이다”라는 Agent 보고 |
| Uptime | DBMS 또는 system이 마지막으로 시작된 후 중단 없이 운영된 시간 | 36시간 |
| Transaction | 여러 DB 변경을 하나의 업무 단위로 처리하는 묶음 | 주문 생성과 재고 감소 |
| Lock Wait | 다른 transaction이 사용 중인 데이터를 변경하기 위해 기다리는 상태 | 주문 A 수정이 끝나기를 주문 B 수정이 대기 |
| Slow Query | 기준보다 오래 걸리거나 많은 데이터를 검사하는 SQL | 평균 10초가 걸리는 조회 |
| Logical Backup | table 구조와 데이터를 SQL 등 논리적 형태로 저장한 백업 | `mysqldump` 파일 |
| Cleanup | 임시로 만든 자원을 작업 후에 정리하는 행위 | 복원 검증용 임시 DB 제거 |

### 1.2 Job과 Task를 구분하는 법

“production DB를 백업하고 복원 가능한지 확인해 달라”는 하나의 **Job**이다. 이 Job을 완료하기 위해 Agent가 수행하는 “MySQL backup 파일 생성”과 “임시 DB에 복원하여 검증”은 각각의 **Task**다.

- Job: 사용자가 달성하려는 운영 목표.
- Task: 해당 목표를 위해 system이 실행하는 구체적인 일.

## 2. 핵심 용어

| 표준 용어 | 코드 | 정의 | 피할 표현 |
|---|---|---|---|
| DB FleetOps | `DB FleetOps` | 관리 DB의 상태와 운영 작업을 중앙 관리하는 플랫폼 | Fleet, 모니터링 툴로만 축약 |
| Control Plane | `control plane` | 메타데이터·정책·Job을 관리하는 Java 시스템 | Server, Master |
| Console | `console` | Control Plane API를 사용하는 운영자 UI | Admin이라는 모호한 표현 |
| Agent | `Agent` | DB host 근처에서 허용된 Task를 실행하는 프로세스이자 등록된 실행 주체 | Worker. Worker는 Control Plane Job consumer에만 사용 |
| Worker | `Worker` | 실행 가능한 Operation Job을 가져가고, 작업 순서와 상태를 조정하는 Control Plane 구성 요소 | Agent |
| 관리 DB | `ManagedDatabase` | FleetOps Inventory에 등록된 DB 인스턴스 | Target DB, Database Inventory Item을 개체명으로 사용 |
| Metadata DB | metadata database | FleetOps 자체의 Entity와 이력을 저장하는 DB | Target DB |
| DB Engine | `DatabaseEngine` | MySQL, PostgreSQL 같은 DBMS 종류 | databaseType, engineType의 무분별한 혼용 |
| Credential | `DatabaseCredential` | 관리 DB에 접속하기 위한 인증 정보 | Connection Info. host/port는 Credential이 아님 |
| 활성 상태 | `DatabaseStatus` | 관리 DB가 FleetOps 작업 대상인지를 나타내는 `ACTIVE|INACTIVE` | Health Status |
| 건강 상태 | `HealthStatus` | 점검 결과로 판단한 `HEALTHY|DEGRADED|CRITICAL|UNKNOWN` | 활성 상태 |
| 연결 상태 | health check result | 한 번의 연결 점검 결과인 `UP|DOWN` | 건강 상태와 동의어로 사용 |
| Health Check | health check | DB 연결 가능 여부와 latency를 확인하는 점검 | Diagnostics |
| Diagnostics | diagnostics | 버전·세션·트랜잭션 등 DB 운영 상태를 조회하는 진단 | Health Check |

## 3. 운영 작업 용어

| 표준 용어 | 코드 | 정의 | 구분 |
|---|---|---|---|
| 운영 Job | `OperationJob` | 사용자의 하나의 운영 목적과 전체 상태·결과 | Task보다 상위 |
| 운영 Task | `OperationTask` | Agent가 실행하는 구체적인 단위 | Job 없이도 생성 가능한 현행 모델 |
| Job Type | `JobType` | 백업·설정 점검·설정 적용·재시작 같은 운영 목적 | Task Type과 구분 |
| Task Type | `OperationTaskType` | Linux 상태 수집·MySQL logical backup·restore verify 같은 실행 계약 | Job Type과 구분 |
| Claim | `claim` | Worker가 실행 가능한 Job의 한시적 소유권을 획득하는 행위 | Task poll과 구분 |
| Lease | `lease` | Worker의 Job 소유권이 유효한 기간 | DB lock과 동일한 개념이 아님 |
| Poll | `nextTask`/poll | Agent가 실행할 다음 Task를 Control Plane에 요청하는 행위 | Worker claim과 구분 |
| Idempotency Key | `idempotencyKey` | 동일 운영 요청의 중복 생성을 방지하는 사용자 제공 key | Entity ID |
| Retry | `retry` | 실패한 같은 Job을 다시 `QUEUED`로 돌려 재실행하는 행위 | 새 Job 생성 |
| Request Payload | `requestPayload` | Job 유형별 요청 계약의 JSON 표현 | Task parameters |
| Result Payload | `resultPayloadJson` | Task 실행의 구조화된 JSON 결과 | result message |

### 3.1 Agent와 Worker를 구분하는 법

Agent와 Worker는 모두 “일을 처리한다”는 점에서 헷갈리기 쉽다. 하지만 위치와 책임이 다르다.

- Worker는 Control Plane 안에서 대기 중인 Job을 고르고 실행 순서를 조정한다. 공장의 작업 관리자에 가깝다.
- Agent는 DB host 근처에서 backup program 실행과 같은 실제 Task를 수행한다. 현장의 작업자에 가깝다.

Claim과 Lease는 두 Worker가 같은 Job을 동시에 처리하지 않게 한다. Worker A가 Job을 claim하면 lease가 유효한 동안은 Worker A가 담당자다. Worker A가 중단되고 lease가 끝나면 다른 Worker가 해당 Job을 이어받을 수 있다.

## 4. 설정 정책 용어

| 표준 용어 | 코드 | 정의 | 피할 표현 |
|---|---|---|---|
| Configuration | configuration | DBMS 운영 parameter와 값의 집합 | Config는 코드 이름 외에서 자제 |
| Configuration Profile | `ConfigurationProfile` | 특정 engine·환경·버전 범위에 대한 Desired State | Policy라는 단독 표현 |
| Profile Parameter | `ConfigurationProfileParameter` | Profile에 속한 하나의 parameter 규칙 | Snapshot Item |
| Desired State | desired state | Profile이 정의한 기대 설정 상태 | expected snapshot |
| Configuration Snapshot | `ConfigurationSnapshot` | 특정 시점에 DB에서 수집한 Actual State | Profile |
| Actual State | actual state | DB에서 관찰된 실제 설정 상태 | current profile |
| Configuration Drift | `ConfigurationDrift` | Desired State와 Actual State의 비교 결과 및 차이 | Snapshot 그 자체 |
| Compliance | `ComplianceStatus` | parameter가 기대값과 일치하는지의 판정 | Apply result |
| Compliant | `COMPLIANT` | 실제 값이 기대값과 일치 | Healthy |
| Non-compliant | `NON_COMPLIANT` | 실제 값이 존재하지만 기대값과 불일치 | Missing |
| Missing | `MISSING` | 필요한 parameter를 Actual State에서 찾을 수 없음 | Non-compliant |
| Configuration Apply | `ConfigurationApply` | 검증된 parameter 변경을 DB에 적용하고 결과를 확인하는 운영 행위 | Profile activation |
| Dynamic Parameter | `dynamic` | DB 재시작 없이 변경 가능한 parameter | applyAllowed |
| Apply Allowed | `applyAllowed` | FleetOps가 해당 parameter를 변경해도 된다는 정책 | dynamic |
| Before/After Snapshot | `beforeSnapshotId`, `afterSnapshotId` | Apply 전·후에 수집한 설정 상태 | Backup |

### 4.1 설정 점검과 적용 예시

production MySQL의 `max_connections`가 100이고 회사 정책은 200이어야 한다고 가정한다.

- Profile: “production MySQL의 `max_connections`는 200”이라는 기준을 보관한다.
- Snapshot: DB에서 현재 값 100을 수집한다.
- Drift: 기대값 200과 실제값 100이 다르므로 `NON_COMPLIANT`라고 판정한다.
- Apply: 정책상 변경이 허용된 parameter라면 200으로 변경한다.
- Before/After Snapshot: 변경 전에 100이었고 변경 후에 200이 되었는지 기록하고 확인한다.

`dynamic=true`라고 해서 FleetOps가 바로 변경할 수 있는 것은 아니다. DBMS가 재시작 없이 변경을 지원하고(`dynamic`), 동시에 운영 정책이 FleetOps의 변경을 허용해야(`applyAllowed`) 한다.

## 5. 백업과 복원 검증 용어

| 표준 용어 | 코드 | 정의 | 구분 |
|---|---|---|---|
| Logical Backup | `MYSQL_LOGICAL_BACKUP` | `mysqldump` 같은 논리 형식의 DB 백업 | Physical backup은 현재 범위 아님 |
| Backup Artifact | backup file | Agent가 생성한 백업 산출물 | 복원 가능 보장 자체는 아님 |
| Restore Verification | `BackupRestoreVerification` | 백업 산출물을 임시 DB에 복원하여 사용 가능성을 확인하는 과정 | Backup execution |
| Temporary Database | `temporaryDatabaseName` | 복원 검증을 위해 일시적으로 생성하는 DB | 원본 DB |
| Cleanup | cleanup | 복원 검증 후 임시 DB를 제거하는 행위 | Verification |
| Verified | `VERIFIED` | 복원과 표 단위 검증이 성공한 상태 | Cleanup success까지 의미하지 않음 |
| Cleanup Failed | `CLEANUP_FAILED` | 복원 또는 검증 후 임시 DB 제거가 실패한 상태 | Verification failed |

## 6. 상태 용어

### 6.1 Agent

| 상태 | 의미 |
|---|---|
| `ONLINE` | 등록 또는 최근 heartbeat로 사용 가능하다고 판단 |
| `OFFLINE` | heartbeat 기준을 넘겨 일시적으로 사용 불가 |
| `UNKNOWN` | 현재 상태를 판단할 정보가 부족 |
| `DISABLED` | 관리자가 사용을 금지 |

### 6.2 Job과 Task

| 상태 | 의미 |
|---|---|
| `QUEUED` | 실행 대기 중 |
| `RUNNING` | Worker 또는 Agent가 실행 중 |
| `SUCCEEDED` | 정의된 성공 기준을 충족하고 종료 |
| `FAILED` | 실행이 실패해 종료. Job은 재시도 가능할 수 있음 |
| `CANCELLED` | 명시적 취소로 종료 |
| `TIMED_OUT` | Job의 허용 실행 시간을 초과해 종료 |

### 6.3 Configuration Apply Item

| 상태 | 의미 |
|---|---|
| `PENDING` | 적용 전 |
| `APPLIED` | DB에 변경 명령을 적용했으나 결과값은 미검증 |
| `VERIFIED` | 적용 후 값이 요청값과 일치 |
| `SKIPPED` | 정책상 실행하지 않음 |
| `UNSUPPORTED` | 현재 DBMS/Adapter가 적용을 지원하지 않음 |
| `FAILED` | 적용 또는 검증 중 실패 |

## 7. 현재 불일치와 정리 후보

| 현재 표현 | 문제 | 정리 후보 |
|---|---|---|
| `ManagedDatabase`, Database Instance, Target DB, Inventory DB | 같은 대상을 여러 이름으로 표현 | 도메인은 `ManagedDatabase`, 문서는 `관리 DB` |
| `database.DatabaseStatus` | Health 상태로 오인 가능 | `ManagedDatabaseStatus` 검토 |
| `health.DatabaseStatus` | 다른 패키지의 동명 enum | `ConnectivityStatus` 또는 기본 흐름 제거 검토 |
| `DatabaseEngine`, `ConfigurationEngineType` | 같은 DBMS 분류를 중복 표현 | 공유 value 또는 명시적 mapper 선택 |
| `databaseType`, `engine`, `engineType` | API·도메인별 필드명 불일치 | 새 계약은 `engine` 우선 |
| AgentTask | 이전 설계명이 문서에 남음 | `OperationTask` |
| Restore Verify, Restore Verification | 동사형·명사형 혼재 | 개념명은 `Restore Verification`, Task Type은 `MYSQL_RESTORE_VERIFY` |
| Apply Status | Apply 전체와 Item 상태가 모호 | `ConfigurationApplyStatus`, `ConfigurationApplyItemStatus` 전체명 사용 |
| Profile status `ACTIVE` | DB의 `ACTIVE`와 의미가 다름 | 항상 `Profile Status`로 문맥 명시 |

## 8. 명명 규칙

- Entity: 식별성과 lifecycle이 있는 명사 (`OperationJob`).
- Value Object: 값 자체가 의미이며 불변인 명사 (`ConnectionSummary`).
- 명령/요청 DTO: 사용자 의도를 나타내는 동사+Request/Command (`CreateBackupJobRequest`).
- 조회 응답 DTO: 대상+Response (`OperationJobResponse`).
- 도메인 행위: 기술적 setter보다 용어집의 동사 (`start`, `retry`, `deactivate`, `markVerified`).
- boolean: 질문으로 읽히는 이름 (`isActive`, `tokenMatches`).
- 시각: 이벤트 발생 시점은 `-edAt` (`createdAt`, `completedAt`), 만료는 `-Until` (`leaseUntil`).
- ID 참조: 대상명+`Id` (`operationJobId`). `targetDatabaseId`/`databaseId`의 통일은 Job 리팩토링 때 결정한다.

## 9. 미확정 용어

다음은 코드 변경 전에 팀 합의가 필요하다.

- `관리 DB`와 `DB 인스턴스` 중 사용자 문서의 최종 표현.
- `Inventory`를 목록/컨텍스트명으로 계속 사용할지.
- 연결 상태 `UP|DOWN`과 건강 상태 4단계를 모두 유지할지.
- `Policy` 컨텍스트의 한국어를 `설정 정책`으로 확정할지.
- 부분 성공 Apply/Job의 상위 성공 판정 용어.
- Backup, Restore Verification, Cleanup의 성공 경계와 최종 사용자 표시 문구.
