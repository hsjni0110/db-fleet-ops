# DB FleetOps 도메인 정리

## 1. 문서의 목적과 상태

이 문서는 DB FleetOps의 요구사항과 도메인 모델을 같은 언어로 정렬하기 위한 기준 문서다. 현재 코드와 `docs` 아래의 설계 기록을 토대로 작성한 **현행 모델 초안**이며, 향후 도메인 합의에 따라 수정한다.

이 문서의 독자는 개발자로 한정하지 않는다. DB 운영자, 기획자, 정책·보안 담당자 등이 코드를 읽지 않고도 다음을 이해할 수 있어야 한다.

- FleetOps가 무엇을 관리하는지
- 각 정보가 왜 필요한지
- 사용자의 요청이 어떻게 실행되고 결과로 남는지
- 어떤 상태 변경이 허용되거나 금지되는지

문서와 코드가 다를 때의 우선순위는 다음과 같다.

1. 합의된 이 문서의 규칙과 용어
2. 실행 가능한 코드와 테스트로 확인된 현행 행위
3. 기존 `docs` 아래의 단계별 설계 기록

기존 개요·아키텍처 문서는 초기 Health/Inventory 단계를 설명하므로 현재 전체 범위를 대표하지 않는다.

## 2. 제품 정의

DB FleetOps는 여러 데이터베이스와 해당 호스트를 중앙에서 등록·관찰하고, 백업과 설정 점검·변경 같은 운영 작업을 안전하게 요청·실행·추적하는 DBMS 운영 관리 플랫폼이다.

쉽게 말하면, 운영자가 여러 DB 서버에 직접 접속해 같은 점검과 변경을 반복하는 대신 FleetOps가 대상·절차·결과를 한곳에서 관리하도록 돕는 시스템이다.

현재 제품은 다음 두 실행 영역으로 구성된다.

- **Control Plane(중앙 관리 영역)**: 관리 대상과 정책을 저장하고, 운영 작업의 순서와 상태를 조율하며, API와 운영자 화면을 제공한다.
- **Agent(현장 실행 프로그램)**: DB가 있는 서버 가까이에서 실행되며, 중앙에 할 일이 있는지 주기적으로 물어보고 미리 허용된 작업만 수행한다.

### 2.1 일을 처리하는 예시

운영자가 production DB의 백업과 복원 검증을 요청하는 경우를 예로 든다.

1. 운영자가 Console에서 관리 DB를 선택하고 백업을 요청한다.
2. Control Plane은 요청 전체를 추적할 `OperationJob`을 만든다.
3. Worker가 Job을 가져가고, Agent가 실행할 백업 `OperationTask`를 만든다.
4. Agent는 Task를 가져가 백업 파일을 만들고 결과를 보고한다.
5. 복원 검증이 요청되었다면 Agent가 임시 DB에 파일을 복원하고 table과 row를 확인한다.
6. Control Plane은 Job, Task, 복원 검증의 결과를 저장하고 운영자에게 최종 상태를 보여준다.

이처럼 Job은 “왜 하는가”와 전체 결과를, Task는 “현장에서 무엇을 실행하는가”를 나타낸다.

## 3. 전체 요구사항

### 3.1 관리 대상 DB

- 운영자는 관리 대상 DB 인스턴스를 등록·조회·수정·비활성화할 수 있어야 한다.
- DB 접속 정보와 자격 증명은 분리하고, 자격 증명은 API 응답에 노출하지 않아야 한다.
- 비활성 DB는 새로운 점검이나 운영 작업의 대상이 되어서는 안 된다.
- DBMS 종류에 따른 접속·진단·설정 차이는 Port/Adapter 경계 뒤로 격리한다.

### 3.2 건강 점검과 진단

- 시스템은 DB 연결 가능 여부와 응답 시간을 점검하고 결과를 남겨야 한다.
- 연결 실패는 인증 실패, 연결 거부, 시간 초과, 호스트 탐색 실패, 알 수 없는 오류로 분류한다.
- 운영자는 버전, uptime, 연결, 세션, 장기 트랜잭션, lock wait, slow query 정보를 조회할 수 있어야 한다.
- 진단은 임의 SQL 실행 기능이 아니라 제한된 진단 유스케이스로 제공한다.

### 3.3 Agent 관리

- Agent는 고유 token으로 등록하고 heartbeat를 보내야 한다.
- heartbeat를 수신한 Agent는 `ONLINE`이 되며, 관리자가 비활성화한 Agent는 heartbeat를 수신할 수 없다.
- Agent는 CPU·memory·disk 사용률과 수집 시각을 보고할 수 있어야 한다.
- Agent는 임의 명령이 아니라 미리 정의된 Task Type만 실행한다.

### 3.4 운영 작업

- 시간이 걸리는 작업은 동기 API 처리가 아니라 `OperationJob`으로 생성한다.
- Job 생성은 DB, Job Type, Idempotency Key 조합으로 중복을 제어한다.
- Worker는 실행 가능한 Job을 claim하고 lease로 소유권을 표현한다.
- 실패한 Job은 최대 횟수 안에서 재시도할 수 있어야 한다.
- Job은 운영 요청과 전체 결과를, Task는 Agent가 실행할 구체적 단위를 표현한다.
- 현재 Job Type은 백업, 설정 점검, 설정 적용, 재시작이며 재시작은 아직 완전한 실행 흐름이 없다.

### 3.5 설정 정책과 Drift

- Configuration Profile은 DBMS·환경·버전 범위에 따른 바람직한 설정(Desired State)을 표현한다.
- Snapshot은 특정 시점의 실제 설정(Actual State)을 표현한다.
- Drift는 같은 DBMS의 Profile과 Snapshot을 비교한 결과다.
- 설정값은 `STRING`, `NUMBER`, `BOOLEAN` 규칙으로 비교하며 문자열 동등성만으로 판단하지 않는다.
- Profile Parameter는 필수 여부, 동적 변경 가능 여부, FleetOps 적용 허용 여부를 구분한다.

### 3.6 안전한 설정 적용

- 설정 변경은 Profile에 정의되고 적용이 허용된 동적 parameter만 대상으로 한다.
- 적용 전·후 Snapshot을 남기고, 각 parameter의 요청값·이전값·결과값과 상태를 추적한다.
- 하나의 DB에 대해 동시에 여러 Apply가 실행되지 않도록 한다.
- 일부 항목만 성공한 경우를 전체 성공과 구분한다.

### 3.7 백업과 복원 검증

- logical backup은 파일 생성만으로 최종 성공이라고 판단하지 않는다.
- 복원 검증을 요청하면 임시 DB에 복원한 후 table 존재와 row count를 확인한다.
- 복원 성공과 임시 DB cleanup 성공을 구분해 기록한다.
- 대용량 DB의 표본 검증·성능 정책은 후속 설계 대상이다.

### 3.8 감사와 관측성

- 중요 운영 행위는 수행 주체, 행위, 대상, 결과, 메시지를 감사 기록으로 남겨야 한다.
- API와 Worker는 분리 실행할 수 있고, 작업 상태를 metric과 log로 관찰할 수 있어야 한다.

## 4. 바운디드 컨텍스트 초안

| 컨텍스트 | 책임 | 주요 모델 | 다른 컨텍스트와의 연결 |
|---|---|---|---|
| Inventory | 관리 DB와 자격 증명 관리 | ManagedDatabase, DatabaseCredential | 다른 모듈은 `databaseId`로 참조 |
| Health | DB 연결 상태와 운영 진단 | DatabaseHealthResult, 진단 value | Inventory의 DB/credential 사용 |
| Agent | 호스트 작업 실행 주체와 metric | Agent, AgentHostMetric | Task가 `agentId`로 지정 |
| Operation | 오래 걸리는 운영 요청을 작은 실행 단위로 나누고 순서·상태를 조정 | OperationJob, OperationTask | DB, Agent, Policy, Backup 조정 |
| Configuration Policy | Desired/Actual 설정 비교와 안전한 적용 | Profile, Snapshot, Drift, Apply | DB와 Job을 ID로 참조 |
| Backup Verification | 백업 산출물의 복원 가능성 검증 | BackupRestoreVerification, Item | Job과 Task를 ID로 참조 |
| Audit | 운영 행위 이력 | AuditLog | application port를 통해 기록 |

`policy`는 현재 하나의 패키지에 Profile·Snapshot·Drift·Apply를 모두 포함한다. 점진적 개선 중에는 일단 하나의 컨텍스트로 다루되, 규칙과 변경 빈도가 달라지면 분리를 재검토한다.

## 5. 도메인 모델의 속성과 행위

### 5.0 모델 분류 기준

| 분류 | 판단 기준 |
|---|---|
| Aggregate(집합) | 항상 같이 변경되어야 하는 도메인 객체의 묶음이다. 예를 들어 Apply와 각 Apply Item은 전체 결과 수가 항상 맞아야 하므로 하나의 집합으로 볼 수 있다. |
| Aggregate Root(집합 대표) | 집합 밖에서 직접 사용하는 대표 객체다. 외부는 구성원을 직접 바꾸지 않고 대표를 통해야 한다. 예: `ConfigurationApply`. |
| Entity(식별되는 개체) | 고유 식별자가 있어 속성이 변해도 같은 대상으로 추적한다. 이름이 바뀌어도 같은 관리 DB인 것과 같다. Aggregate Root도 Entity의 한 종류다. |
| Value Object(값 객체) | 고유 번호보다 값 자체가 중요하다. 예: “현재 연결 10개, 최대 100개”라는 연결 요약. 보통 생성 후 변경하지 않는다. |
| Domain Service(도메인 서비스) | 여러 개체를 함께 사용해야 해서 하나의 개체에 담기 어려운 업무 규칙을 수행한다. 예: Profile과 Snapshot의 설정값 비교. |

`lifecycle`은 개체가 생성되고 상태가 바뀌며 종료되는 전체 과정을 뜻한다. `Repository`는 도메인 객체를 저장하고 다시 찾는 통로다. `불변식`은 어떤 상태에서도 반드시 지켜야 하는 규칙이다. 예를 들어 “완료된 Job은 다시 시작할 수 없다”는 불변식이다.

“현재 구현”에 나오는 `JPA Entity`는 DB table에 저장되는 Java 객체라는 뜻이다. `Java record`는 여러 값을 하나로 묶어 전달하는 간결한 Java 표현 방식이다. 이들은 코드가 현재 정보를 어떻게 저장·표현하는지 알려 주기 위한 기술 설명이며, 업무적 의미는 아래의 “도메인 분류”로 판단한다.

`@Entity`는 JPA 저장 방식을 나타낼 뿐 Aggregate Root임을 의미하지 않는다. 따라서 각 모델은 다음 두 관점으로 구분한다.

- **현재 구현**: JPA Entity, Java record 등 코드에서 확인되는 기술적 형태.
- **도메인 분류**: 현재 책임과 목표 aggregate 경계를 기준으로 한 DDD 역할. 경계 합의가 필요하면 `후보` 또는 `의도된 구성원`으로 표시한다.

### 5.1 Inventory

#### ManagedDatabase

- 의미: FleetOps가 관리하는 DB 인스턴스.
- 현재 구현: JPA Entity, 독립 Repository로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Inventory Aggregate의 진입점 후보다.

속성:

- `id`: 관리 DB의 고유 식별자.
- `name`: FleetOps에서 관리 DB를 구분하기 위한 표시 이름.
- `host`: DB에 접속할 호스트명 또는 IP 주소.
- `port`: DB가 연결을 수신하는 TCP port.
- `databaseName`: 접속할 논리 DB 이름.
- `engine`: DBMS 종류. 현재 `MYSQL`, `POSTGRESQL`을 표현한다.
- `status`: FleetOps의 관리 대상 여부. `ACTIVE` 또는 `INACTIVE`다.
- `environment`: DB가 속한 운영 환경. 예: production, staging.
- `serviceName`: DB를 사용하는 서비스의 이름.
- `owner`: DB의 관리 책임자 또는 책임 팀.
- `description`: DB에 대한 부가 설명.
- `createdAt`: 관리 DB가 등록된 시각.
- `updatedAt`: 관리 DB가 마지막으로 변경된 시각.

행위:

- `ManagedDatabase(...)`: 관리 DB를 생성하고 상태를 `ACTIVE`로 초기화한다.
- `update(...)`: 이름, 접속점, engine, 환경, 소유자 등 관리 정보를 수정한다.
- `deactivate()`: 상태를 `INACTIVE`로 변경하여 새 운영 작업의 대상에서 제외한다.
- `isActive()`: 현재 상태가 `ACTIVE`인지 판단한다.

- 불변식 보완 필요: host/name 빈 값, port 범위, engine 필수 검증이 도메인 내부에 없고 `update()`가 `updatedAt`을 변경하지 않는다.

#### DatabaseCredential

- 의미: 관리 DB에 접속하기 위한 자격 증명.
- 현재 구현: JPA Entity, `DatabaseCredentialRepository`로 독립 저장·조회.
- 도메인 분류: **Entity, ManagedDatabase Aggregate의 의도된 구성원**. 현재는 ID만으로 연결되고 Repository도 분리되어 실제 aggregate 경계는 코드에서 보장되지 않는다.

속성:

- `id`: credential의 고유 식별자.
- `databaseId`: credential을 사용하는 관리 DB의 식별자.
- `username`: DB 인증에 사용할 계정명.
- `password`: DB 인증에 사용할 비밀번호.
- `createdAt`: credential이 생성된 시각.
- `updatedAt`: credential이 마지막으로 교체된 시각.

행위:

- `DatabaseCredential(...)`: 관리 DB의 username과 password를 가진 credential을 생성한다. 관리 DB 식별자와 빈 값이 아닌 username·password가 모두 필요하다.
- `changeCredentials(String username, String password)`: username과 password를 하나의 credential 단위로 교체하고 `updatedAt`을 변경한다. 두 값 중 하나라도 `null`, 빈 문자열, 공백만 있는 문자열이면 변경하지 않는다.

불변식:

- `databaseId`는 `null`일 수 없다.
- `username`과 `password`는 `null`, 빈 문자열, 공백만 있는 문자열일 수 없다.
- 잘못된 credential 변경 요청은 기존 username과 password를 변경하지 않는다.

- 보안 보완 필요: 현재 password가 암호화나 secret reference 없이 저장되며 getter로 노출된다.

### 5.2 Health

#### DatabaseHealth

- 의미: 기본 DB 접속 점검의 즉시 결과 value.
- 현재 구현: Java record, JPA와 무관한 불변 객체.
- 도메인 분류: **Value Object**. 식별자나 별도 lifecycle 없이 한 번의 접속 점검 결과를 값으로 표현한다.

속성:

- `databaseType`: 점검한 DBMS 종류의 문자열 표현.
- `host`: 점검한 DB host.
- `port`: 점검한 DB port.
- `status`: 연결 결과. `UP` 또는 `DOWN`이다.
- `latencyMs`: 연결 점검에 소요된 millisecond.
- `checkedAt`: 접속을 점검한 시각.
- `errorCode`: 접속 실패 분류. 성공 시 `null`이다.
- `message`: 점검 결과를 설명하는 메시지.

행위:

- `up(...)`: 성공한 `UP` 접속 점검 결과를 생성한다.
- `down(...)`: error code와 message를 포함한 `DOWN` 접속 점검 결과를 생성한다.

#### DatabaseHealthResult

- 의미: Inventory에 등록된 DB의 저장된 health check 결과.
- 현재 구현: JPA Entity, 독립 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity 후보**. 각 점검 결과가 독립적으로 저장되지만, 현재는 도메인 행위와 명시적 식별자 조회가 부족해 append-only 기록 모델에 가깝다.

속성:

- `id`: health check 결과의 고유 식별자. 현재 getter는 없다.
- `databaseId`: 점검한 관리 DB의 식별자.
- `status`: 판단된 건강 상태. `HEALTHY`, `DEGRADED`, `CRITICAL`, `UNKNOWN` 중 하나다.
- `connectionSuccess`: DB 연결 성공 여부.
- `responseTimeMs`: health check 응답 시간.
- `message`: health check 결과 설명.
- `checkedAt`: health check를 수행한 시각.

행위:

- `DatabaseHealthResult(...)`: 한 번의 health check 결과를 생성하고 `checkedAt`을 기록한다.

- 통합 필요: 두 모델이 상태·시간 타입·생성 규칙이 다르다. 기본 DB 점검을 Inventory 흐름으로 편입할지 결정해야 한다.

#### Diagnostic values

- 현재 구현: 모두 Java record.
- 도메인 분류: **Value Object**. DB 진단 시점의 조회 결과를 불변 값으로 표현한다.

- `DatabaseVersionInfo.version`: DBMS가 보고한 버전.
- `DatabaseUptimeInfo.uptimeSeconds`: DBMS가 시작된 후 경과한 초.
- `ConnectionSummary.currentConnections`: 현재 열려 있는 연결 수.
- `ConnectionSummary.runningConnections`: 현재 작업을 수행 중인 연결 수.
- `ConnectionSummary.maxConnections`: DBMS가 허용하는 최대 연결 수.
- `ConnectionSummary.usagePercent`: 최대 연결 대비 현재 연결 사용률.
- `SessionInfo.processId`: DB session/process 식별자.
- `SessionInfo.user`: session의 DB 계정.
- `SessionInfo.host`: session client의 host.
- `SessionInfo.databaseName`: session이 선택한 DB 이름.
- `SessionInfo.command`: session이 수행 중인 command.
- `SessionInfo.timeSeconds`: 현재 session 상태가 지속된 초.
- `SessionInfo.state`: DBMS가 보고한 session 상태.
- `SessionInfo.queryPreview`: 실행 SQL의 제한된 미리보기.
- `LongTransactionInfo.transactionId`: 장기 transaction 식별자.
- `LongTransactionInfo.state`: transaction 상태.
- `LongTransactionInfo.startedAt`: transaction 시작 시각.
- `LongTransactionInfo.durationSeconds`: transaction 지속 시간.
- `LongTransactionInfo.threadId`: transaction을 수행하는 DB thread 식별자.
- `LongTransactionInfo.queryPreview`: transaction SQL의 제한된 미리보기.
- `LockWaitInfo.waitingTransactionId`: lock을 기다리는 transaction 식별자.
- `LockWaitInfo.waitingThreadId`: lock을 기다리는 thread 식별자.
- `LockWaitInfo.waitingQueryPreview`: lock을 기다리는 SQL 미리보기.
- `LockWaitInfo.blockingTransactionId`: lock을 점유한 transaction 식별자.
- `LockWaitInfo.blockingThreadId`: lock을 점유한 thread 식별자.
- `LockWaitInfo.blockingQueryPreview`: lock을 점유한 SQL 미리보기.
- `SlowQueryInfo.digestText`: 정규화된 SQL 문장.
- `SlowQueryInfo.executionCount`: 해당 SQL pattern의 실행 횟수.
- `SlowQueryInfo.averageSeconds`: 평균 실행 시간.
- `SlowQueryInfo.maxSeconds`: 최대 실행 시간.
- `SlowQueryInfo.rowsExamined`: 조회 중 검사한 row 수.
- `SlowQueryInfo.rowsSent`: client에게 반환한 row 수.
- 행위: 현재 모두 Java `record`인 불변 조회 value이며 별도의 도메인 메서드는 없다.

### 5.3 Agent

#### Agent

- 의미: Control Plane에 등록된 호스트 작업 실행자.
- 현재 구현: JPA Entity, 독립 Repository로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Agent 등록·인증·상태 lifecycle의 진입점이다.

속성:

- `id`: Agent의 고유 식별자.
- `agentName`: Control Plane에서 Agent를 구분하는 이름.
- `hostname`: Agent가 실행되는 host의 hostname.
- `ipAddress`: Agent host의 IP 주소.
- `osName`: Agent host의 운영체제 이름.
- `architecture`: Agent binary가 실행되는 CPU architecture. 빈 값은 `unknown`으로 정규화한다.
- `agentVersion`: 실행 중인 Agent software 버전.
- `agentToken`: Agent 인증에 사용하는 token.
- `status`: `ONLINE`, `OFFLINE`, `UNKNOWN`, `DISABLED` 중 하나인 Agent 상태.
- `lastHeartbeatAt`: 마지막 heartbeat를 수신한 시각.
- `createdAt`: Agent가 등록된 시각.
- `updatedAt`: Agent 상태가 마지막으로 변경된 시각.

행위:

- `register(...)`: Agent를 등록하고 `ONLINE`으로 초기화한다. architecture를 받는 형태와 `unknown`을 사용하는 형태가 있다.
- `heartbeat()`: 비활 Agent가 아니면 `ONLINE`으로 변경하고 heartbeat/수정 시각을 갱신한다.
- `markOffline()`: 비활 Agent가 아니면 `OFFLINE`으로 변경한다.
- `disable()`: Agent를 `DISABLED`로 변경한다.
- `tokenMatches(String token)`: 제공된 token과 Agent token의 일치 여부를 판단한다.

- 규칙: 등록 시 `ONLINE`; 비활 Agent는 heartbeat 금지; 비활 Agent의 offline 처리는 무시.

#### AgentHostMetric

- 의미: Agent host의 한 시점 자원 사용률.
- 현재 구현: JPA Entity, 독립 Repository로 저장.
- 도메인 분류: **Entity, Agent Aggregate의 의도된 구성원**. 시계열 metric을 Agent Aggregate 안에 포함할지 별도 Metric Aggregate로 다룰지는 저장량과 lifecycle을 기준으로 추가 확정해야 한다.

속성:

- `id`: host metric의 고유 식별자.
- `agentId`: metric을 보고한 Agent의 식별자.
- `cpuUsagePercent`: CPU 사용률.
- `memoryUsagePercent`: memory 사용률.
- `diskUsagePercent`: disk 사용률.
- `collectedAt`: Agent가 metric을 수집한 시각.

행위:

- `create(...)`: Agent의 CPU, memory, disk 사용률과 수집 시각을 가진 metric을 생성한다.

- 보완 필요: 사용률의 0~100 범위를 검증하지 않는다.

### 5.4 Operation

#### OperationJob

- 의미: 사용자가 요청한 하나의 운영 목적과 전체 실행 결과.
- 현재 구현: JPA Entity, 독립 Repository로 저장. optimistic locking(두 Worker가 같은 Job을 동시에 변경하는 것을 감지하는 방식)을 사용한다.
- 도메인 분류: **Aggregate Root / Entity**. 운영 요청의 전체 lifecycle과 결과를 책임진다.

속성:

- `id`: Job의 고유 식별자.
- `jobType`: 운영 목적. `BACKUP`, `CONFIGURATION_CHECK`, `CONFIGURATION_APPLY`, `RESTART` 중 하나다.
- `targetDatabaseId`: Job이 대상으로 하는 관리 DB 식별자.
- `status`: Job의 현재 lifecycle 상태.
- `requestedBy`: Job을 요청한 사용자 또는 시스템.
- `idempotencyKey`: 동일한 Job 중복 생성을 방지하는 key.
- `requestPayload`: Job Type별 요청 parameter를 담은 JSON 문자열.
- `priority`: Job 실행 우선순위. 현재 기본값은 0이다.
- `retryCount`: 이미 수행한 재시도 횟수.
- `maxRetryCount`: 허용된 최대 재시도 횟수. 현재 기본값은 3이다.
- `leaseOwner`: Job을 claim한 Worker의 식별자.
- `leaseUntil`: Worker의 Job 소유권이 만료되는 시각.
- `availableAt`: Job이 claim 가능해지는 시각.
- `startedAt`: Job 실행이 시작된 시각.
- `finishedAt`: Job이 종료 상태에 도달한 시각.
- `resultCode`: Job 결과를 분류하는 code.
- `resultMessage`: Job 결과의 상세 설명.
- `version`: 동시 변경을 감지하기 위한 optimistic-lock version.
- `createdAt`: Job이 생성된 시각.
- `updatedAt`: Job이 마지막으로 변경된 시각.

행위:

- `create(...)`: `QUEUED` 상태의 Job을 생성한다. request payload를 받는 overload가 있다.
- `start(String workerId, LocalDateTime leaseUntil)`: `QUEUED` Job을 `RUNNING`으로 변경하고 lease를 설정한다.
- `succeed(String resultMessage)`: `RUNNING` Job을 `SUCCEEDED`로 종료한다.
- `fail(String resultCode, String resultMessage)`: `RUNNING` Job을 `FAILED`로 종료한다.
- `retry(LocalDateTime nextAvailableAt)`: 재시도 횟수가 남은 `FAILED` Job을 `QUEUED`로 돌리고 다음 실행 가능 시각을 설정한다.
- `cancel()`: 성공하지 않았고 이미 취소되지 않은 Job을 `CANCELLED`로 종료한다.
- `timeout()`: `RUNNING` Job을 `TIMED_OUT`로 종료한다.

- 상태 전이: `QUEUED -> RUNNING -> SUCCEEDED|FAILED|TIMED_OUT`; `FAILED -> QUEUED`; `QUEUED|RUNNING|FAILED|TIMED_OUT -> CANCELLED`. 현재 `FAILED` Job을 cancel할 수 있는 점은 정책 확정이 필요하다.

#### OperationTask

- 의미: Agent가 수행하는 구체적인 실행 단위.
- 현재 구현: JPA Entity, 독립 Repository·API·lifecycle로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Job을 ID로 참조하지만 Agent와 독립적으로 상태를 변경하므로 별도 Aggregate로 다루는 것이 현재 구조에 부합한다.

속성:

- `id`: Task의 고유 식별자.
- `agentId`: Task를 실행할 Agent 식별자.
- `operationJobId`: Task를 생성한 Job 식별자. 독립 Task는 `null`일 수 있다.
- `taskType`: Agent가 실행할 허용된 작업 종류.
- `status`: Task의 현재 lifecycle 상태.
- `parametersJson`: Task 실행 parameter를 담은 JSON 문자열.
- `resultPayloadJson`: Task가 반환한 구조화된 JSON 결과.
- `errorCode`: Task 실패 분류 code.
- `errorMessage`: Task 실패의 상세 설명.
- `startedAt`: Agent가 Task 실행을 시작한 시각.
- `completedAt`: Task가 성공 또는 실패로 종료된 시각.
- `createdAt`: Task가 생성된 시각.
- `updatedAt`: Task가 마지막으로 변경된 시각.

행위:

- `create(...)`: Job과 연결되지 않은 `QUEUED` Task를 생성한다.
- `createForJob(...)`: 특정 Job에 속한 `QUEUED` Task를 생성한다.
- `start()`: `QUEUED` Task를 `RUNNING`으로 변경한다.
- `complete(String resultPayloadJson)`: `RUNNING` Task에 결과 payload를 기록하고 `SUCCEEDED`로 종료한다.
- `fail(String errorCode, String errorMessage)`: `RUNNING` Task에 실패 정보를 기록하고 `FAILED`로 종료한다.

- 상태 전이: `QUEUED -> RUNNING -> SUCCEEDED|FAILED`.
- 불일치: enum에 `CANCELLED`가 있지만 현재 도메인 행위로는 전이할 수 없다.

### 5.5 Configuration Policy

#### ConfigurationProfile

- 의미: 특정 DBMS·환경·버전 범위에 적용할 Desired State의 헤더.
- 현재 구현: JPA Entity, Parameter와 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. Profile의 lifecycle과 Parameter 규칙을 책임지는 Configuration Profile Aggregate의 진입점이다.

속성:

- `id`: Profile의 고유 식별자.
- `profileName`: Profile을 구분하는 이름.
- `engineType`: Profile이 대상으로 하는 DBMS 종류.
- `environment`: Profile을 적용할 운영 환경.
- `versionRange`: Profile과 호환되는 DBMS 버전 범위.
- `description`: Profile의 목적과 적용 기준에 대한 설명.
- `status`: Profile lifecycle 상태. `DRAFT`, `ACTIVE`, `INACTIVE` 중 하나다.
- `createdAt`: Profile이 생성된 시각.
- `updatedAt`: Profile이 마지막으로 변경된 시각.

행위:

- `create(...)`: `DRAFT` 상태의 Profile을 생성한다.
- `activate()`: Profile을 `ACTIVE`로 변경한다.
- `deactivate()`: Profile을 `INACTIVE`로 변경한다.
- `updateDescription(String description)`: Profile 설명을 수정한다.

#### ConfigurationProfileParameter

- 의미: Profile이 정의한 하나의 DBMS parameter 규칙.
- 현재 구현: JPA Entity, Profile과 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationProfile Aggregate의 의도된 구성원**. 현재는 Profile ID만 보유하며 Aggregate Root가 집합 규칙을 직접 보장하지 못한다.

속성:

- `id`: Profile Parameter의 고유 식별자.
- `profileId`: Parameter가 속한 Profile 식별자.
- `parameterName`: DBMS parameter 이름.
- `expectedValue`: Desired State에서 기대하는 parameter 값.
- `valueType`: 값 비교와 검증에 사용할 `STRING`, `NUMBER`, `BOOLEAN` 타입.
- `required`: Actual State에 parameter가 반드시 존재해야 하는지의 여부.
- `dynamic`: DB 재시작 없이 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 parameter를 직접 변경해도 되는지의 여부.
- `description`: Parameter의 의미와 정책에 대한 설명.
- `createdAt`: Parameter 규칙이 생성된 시각.
- `updatedAt`: Parameter 규칙이 마지막으로 변경된 시각.

행위:

- `create(...)`: Profile에 속한 Parameter 규칙을 생성한다. nullable boolean에는 required `true`, dynamic/applyAllowed `false`를 기본값으로 적용한다.
- `updateExpectedValue(String expectedValue, ParameterValueType valueType)`: 기대값과 값 타입을 함께 수정한다.
- `updateApplyPolicy(Boolean dynamic, Boolean applyAllowed)`: 동적 변경 가능 여부와 FleetOps 적용 허용 여부를 수정한다.

- 집합 규칙 보완 필요: Profile이 parameter 집합을 소유하지 않고 Service가 별도 Repository로 조정한다. Active Profile 수정 가능 여부도 확정해야 한다.

#### ConfigurationSnapshot

- 의미: 특정 시점의 DB Actual State 헤더.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 한 번 수집된 Actual State 집합의 진입점이다.

속성:

- `id`: Snapshot의 고유 식별자.
- `databaseId`: 설정을 수집한 관리 DB 식별자.
- `engineType`: 수집 대상 DBMS 종류.
- `capturedAt`: DB 설정을 수집한 시각.

행위:

- `create(Long databaseId, ConfigurationEngineType engineType)`: DB와 engine을 기준으로 Snapshot 헤더를 생성한다.

#### ConfigurationSnapshotItem

- 의미: Snapshot에 수집된 하나의 DBMS parameter 값.
- 현재 구현: JPA Entity, Snapshot과 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationSnapshot Aggregate의 의도된 구성원**. 식별자를 가지지만 Snapshot 생성 후에는 변경하지 않는다.

속성:

- `id`: Snapshot Item의 고유 식별자.
- `snapshotId`: Item이 속한 Snapshot 식별자.
- `parameterName`: 수집한 DBMS parameter 이름.
- `actualValue`: 수집 시점의 실제 parameter 값.
- `unit`: parameter 값의 단위.
- `valueType`: DBMS 또는 Adapter가 보고한 값 타입의 문자열 표현.
- `dynamic`: 수집된 parameter가 동적 변경 가능한지의 여부.
- `source`: parameter 값을 얻은 DBMS view·command 등의 출처.
- `createdAt`: Snapshot Item이 저장된 시각.

행위:

- `create(...)`: Snapshot에 속한 하나의 Actual State Item을 생성한다.

- 타입 불일치: Item의 `valueType`이 enum이 아닌 String이다.

#### ConfigurationDrift

- 의미: Profile과 Snapshot을 비교한 전체 결과.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 하나의 비교 실행과 parameter별 결과 집합을 대표한다.

속성:

- `id`: Drift 결과의 고유 식별자.
- `databaseId`: 비교 대상 관리 DB 식별자.
- `profileId`: Desired State로 사용한 Profile 식별자.
- `snapshotId`: Actual State로 사용한 Snapshot 식별자.
- `engineType`: 비교 대상 DBMS 종류.
- `status`: 전체 비교 결과. `COMPLIANT` 또는 `NON_COMPLIANT`다.
- `totalCount`: 비교한 전체 parameter 수.
- `compliantCount`: 기대값과 일치한 parameter 수.
- `nonCompliantCount`: 존재하지만 기대값과 다른 parameter 수.
- `missingCount`: Actual State에서 찾을 수 없는 parameter 수.
- `checkedAt`: Profile과 Snapshot을 비교한 시각.

행위:

- `create(...)`: 비교 상태와 parameter별 집계를 가진 Drift 결과를 생성한다.

#### ConfigurationDriftItem

- 의미: 하나의 parameter에 대한 Desired/Actual State 비교 결과.
- 현재 구현: JPA Entity, Drift와 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationDrift Aggregate의 의도된 구성원**. 결과 생성 후에는 변경하지 않는다.

속성:

- `id`: Drift Item의 고유 식별자.
- `driftId`: Item이 속한 Drift 식별자.
- `parameterName`: 비교한 DBMS parameter 이름.
- `expectedValue`: Profile이 정의한 기대값.
- `actualValue`: Snapshot에서 확인한 실제값.
- `valueType`: 비교 규칙에 사용한 값 타입.
- `required`: parameter가 Actual State에 반드시 있어야 하는지의 여부.
- `dynamic`: parameter가 동적으로 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 parameter를 변경해도 되는지의 여부.
- `complianceStatus`: `COMPLIANT`, `NON_COMPLIANT`, `MISSING` 중 하나인 비교 결과.
- `message`: 해당 비교 결과의 상세 설명.
- `createdAt`: Drift Item이 생성된 시각.

행위:

- `create(...)`: parameter 하나의 비교 결과를 생성한다.

- 현재 행위는 결과 생성만 있고, 집계 무결성은 생성자 밖 Service에서 보장한다.

#### ConfigurationApply

- 의미: 관리 DB에 설정 변경을 적용하는 전체 운영 행위와 결과.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. Apply lifecycle, 전·후 Snapshot, parameter 결과 집계를 책임진다.

속성:

- `id`: Apply의 고유 식별자.
- `databaseId`: 설정을 변경할 관리 DB 식별자.
- `operationJobId`: Apply의 실행 순서와 상태를 조정하는 Job 식별자.
- `requestedBy`: Apply를 요청한 사용자 또는 시스템.
- `reason`: 설정 변경을 요청한 이유.
- `status`: `REQUESTED`, `RUNNING`, `SUCCEEDED`, `PARTIALLY_SUCCEEDED`, `FAILED`, `CANCELLED` 중 하나인 Apply 상태.
- `totalCount`: 적용 대상 parameter 전체 수.
- `successCount`: 적용과 검증에 성공한 parameter 수.
- `failedCount`: 적용 또는 검증에 실패한 parameter 수.
- `skippedCount`: 정책상 적용하지 않은 parameter 수.
- `beforeSnapshotId`: Apply 시작 전에 수집한 Snapshot 식별자.
- `afterSnapshotId`: Apply 완료 후에 수집한 Snapshot 식별자.
- `createdAt`: Apply 요청이 생성된 시각.
- `startedAt`: Apply 실행이 시작된 시각.
- `completedAt`: Apply가 종료 상태에 도달한 시각.

행위:

- `create(...)`: `REQUESTED` 상태의 Apply를 생성하고 count를 초기화한다.
- `start(Long beforeSnapshotId)`: before Snapshot을 연결하고 `REQUESTED`를 `RUNNING`으로 변경한다.
- `complete(...)`: after Snapshot과 결과 count를 기록하고 `SUCCEEDED`, `PARTIALLY_SUCCEEDED`, `FAILED` 중 하나로 종료한다.
- `fail(...)`: 현재까지의 결과 count를 기록하고 `FAILED` 또는 `PARTIALLY_SUCCEEDED`로 종료한다.
- `cancel()`: 완료 상태가 아닌 Apply를 `CANCELLED`로 종료한다.

#### ConfigurationApplyItem

- 의미: Apply에서 하나의 parameter에 수행한 변경과 검증 결과.
- 현재 구현: JPA Entity, Apply와 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationApply Aggregate의 의도된 구성원**. Parameter 단위 lifecycle을 가지지만 전체 집계는 Apply Root가 보장해야 한다.

속성:

- `id`: Apply Item의 고유 식별자.
- `applyId`: Item이 속한 Apply 식별자.
- `parameterName`: 변경할 DBMS parameter 이름.
- `requestedValue`: DB에 적용하려는 값.
- `beforeValue`: 적용 전에 수집한 parameter 값.
- `afterValue`: 적용 후에 수집하여 검증한 parameter 값.
- `valueType`: parameter 값의 검증·비교 타입.
- `dynamic`: DB 재시작 없이 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 변경해도 되는지의 여부.
- `applyStatus`: `PENDING`, `APPLIED`, `VERIFIED`, `SKIPPED`, `FAILED`, `UNSUPPORTED` 중 하나인 Item 상태.
- `failureCode`: 미적용 또는 실패 이유를 분류하는 code.
- `failureMessage`: 미적용 또는 실패의 상세 설명.
- `createdAt`: Apply Item이 생성된 시각.
- `appliedAt`: DB에 변경을 적용한 시각.
- `verifiedAt`: 적용 후 값을 검증한 시각.

행위:

- `create(...)`: `PENDING` 상태의 parameter Apply Item을 생성한다.
- `markBeforeValue(String beforeValue)`: 변경 전 parameter 값을 기록한다.
- `markApplied()`: `PENDING` Item을 `APPLIED`로 변경하고 적용 시각을 기록한다.
- `markVerified(String afterValue)`: `APPLIED` Item에 변경 후 값을 기록하고 `VERIFIED`로 변경한다.
- `markSkipped(String failureCode, String failureMessage)`: Item을 `SKIPPED`로 종료하고 이유를 기록한다.
- `markUnsupported(String failureCode, String failureMessage)`: Item을 `UNSUPPORTED`로 종료하고 이유를 기록한다.
- `markFailed(String failureCode, String failureMessage)`: Item을 `FAILED`로 종료하고 실패 정보를 기록한다.

- Item 전이는 `PENDING -> APPLIED -> VERIFIED`이며 `SKIPPED|UNSUPPORTED|FAILED`로도 종료할 수 있다.
- 무결성 보완 필요: count 합계와 total의 일치, 음수 금지, `fail()`의 허용 이전 상태, Item의 종료 상태 재변경 금지가 완전히 보장되지 않는다.

### 5.6 Backup Verification

#### BackupRestoreVerification

- 의미: 백업 산출물을 임시 DB에 복원하여 사용 가능성을 확인하는 전체 검증.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 복원 검증 lifecycle과 table별 결과 집계를 대표한다.

속성:

- `id`: Restore Verification의 고유 식별자.
- `operationJobId`: 백업과 복원 검증을 요청한 Job 식별자.
- `backupTaskId`: 백업 파일을 생성한 Task 식별자.
- `restoreVerifyTaskId`: 복원 검증을 실행한 Task 식별자.
- `databaseId`: 백업 원본인 관리 DB 식별자.
- `sourceDatabaseName`: 백업한 원본 논리 DB 이름.
- `backupFile`: 검증할 백업 파일의 경로 또는 식별 정보.
- `temporaryDatabaseName`: 복원 검증에 사용할 임시 DB 이름.
- `status`: `REQUESTED`, `RUNNING`, `VERIFIED`, `FAILED`, `CLEANUP_FAILED` 중 하나인 검증 상태.
- `restoredTableCount`: 임시 DB에 복원된 table 수.
- `checkedTableCount`: 존재와 row count를 확인한 table 수.
- `totalRowCount`: 검증한 table의 row count 합계.
- `errorCode`: 복원·검증·cleanup 실패 분류 code.
- `errorMessage`: 복원·검증·cleanup 실패의 상세 설명.
- `startedAt`: 복원 검증을 시작한 시각.
- `completedAt`: 검증이 종료 상태에 도달한 시각.
- `createdAt`: 검증 요청이 생성된 시각.

행위:

- `create(...)`: 백업·복원 Task와 검증 대상을 연결하고 `REQUESTED`로 초기화한다.
- `start()`: `REQUESTED` 검증을 `RUNNING`으로 변경한다.
- `verify(...)`: `RUNNING` 검증에 table/row 집계를 기록하고 `VERIFIED`로 종료한다.
- `fail(String errorCode, String errorMessage)`: 검증을 `FAILED`로 종료하고 실패 정보를 기록한다. `VERIFIED`에서는 허용하지 않는다.
- `cleanupFailed(String errorCode, String errorMessage)`: `RUNNING` 또는 `VERIFIED` 검증을 `CLEANUP_FAILED`로 변경한다.

- 전이는 `REQUESTED -> RUNNING -> VERIFIED|FAILED|CLEANUP_FAILED`, 또는 `VERIFIED -> CLEANUP_FAILED`다.

#### BackupRestoreVerificationItem

- 의미: 복원된 table 하나의 검증 결과.
- 현재 구현: JPA Entity, Verification과 분리된 Repository로 저장.
- 도메인 분류: **Entity, BackupRestoreVerification Aggregate의 의도된 구성원**. 식별자를 가지고 table별 결과로 추적되며 생성 후에는 변경하지 않는다.

속성:

- `id`: Verification Item의 고유 식별자.
- `verificationId`: Item이 속한 Restore Verification 식별자.
- `tableName`: 검증한 table 이름.
- `existsInRestoredDb`: table이 복원 DB에 존재하는지의 여부.
- `rowCount`: 복원된 table에서 확인한 row 수.
- `status`: `VERIFIED`, `MISSING`, `COUNT_FAILED`, `SKIPPED` 중 하나인 table 검증 결과.
- `message`: table 검증 결과의 상세 설명.
- `createdAt`: table 검증 결과가 생성된 시각.

행위:

- `verified(...)`: table 존재와 row count 확인에 성공한 `VERIFIED` Item을 생성한다.
- `missing(...)`: 복원 DB에 table이 없는 `MISSING` Item을 생성한다.
- `countFailed(...)`: table은 있지만 row count 확인에 실패한 `COUNT_FAILED` Item을 생성한다.
- `skipped(...)`: 검증을 수행하지 않은 `SKIPPED` Item을 생성한다.

- 규칙: 모든 Item은 결과별 named factory로 생성하며 생성 후 변경하지 않는다.

### 5.7 Audit

#### AuditLog

- 의미: 이미 일어난 운영 행위의 불변 기록.
- 현재 구현: JPA Entity, 독립 Repository에 기존 기록을 바꾸지 않고 새 기록만 추가하는 방식(append-only)으로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 각 Audit Log는 다른 개체의 lifecycle에 포함되지 않고 독립적으로 생성·조회되는 불변 기록이다.

속성:

- `id`: Audit Log의 고유 식별자.
- `actor`: 운영 행위를 요청하거나 수행한 사용자·시스템.
- `action`: 수행한 운영 행위의 종류.
- `resourceType`: 행위의 대상이 된 자원 종류.
- `resourceId`: 행위의 대상이 된 자원 식별자.
- `result`: 행위 결과의 문자열 분류.
- `message`: 행위와 결과에 대한 상세 설명.
- `createdAt`: Audit Log가 생성된 시각.

행위:

- `create(...)`: 운영 행위의 주체·대상·결과를 가진 불변 Audit Log를 생성한다.

- 보완 필요: action/resource/result가 문자열이어서 용어 표준을 코드로 강제하지 못한다.

## 6. 현재 모델의 구조적 문제

1. **풍부한 모델과 데이터 모델의 혼재**: Job·Task·Agent·Apply는 상태 행위를 가지지만 Snapshot·Drift·HealthResult는 생성과 집계 규칙을 Service에 의존한다.
2. **ID만으로 연결된 엔티티**: 모든 연관이 `Long` ID이며 aggregate boundary가 코드에 명확히 드러나지 않는다.
3. **시각 생성의 직접 의존**: 도메인이 `LocalDateTime.now()`를 직접 호출해 테스트와 timezone 일관성이 약하다.
4. **중복·모호한 타입**: `database.domain.DatabaseStatus`(관리 상태)와 `health.domain.DatabaseStatus`(연결 상태), `DatabaseEngine`과 `ConfigurationEngineType`이 따로 존재한다.
5. **JSON payload의 약한 계약**: Job/Task의 parameter와 result가 String으로 저장되어 type별 계약이 DTO와 executor에 흩어져 있다.
6. **불변식 공백**: 생성자 validation, 상태 전이, 집계 count, enum과 행위 사이에 빈틈이 있다.
7. **문서 노후화**: 최상위 개요와 architecture 문서가 현재 구현 범위를 반영하지 못한다.

## 7. 점진적 개선 원칙과 순서

### 7.1 원칙

- 한 번에 전체 엔티티를 재설계하지 않고, 하나의 유스케이스와 aggregate씩 문서·코드·테스트를 같이 정렬한다.
- 표현 간결화와 도메인 모델 풍부화를 구분한다. Lombok은 boilerplate를 줄이지만 불변식을 만들지는 않는다.
- Entity에는 `@Data`, public setter, 무분별한 `@Builder` 사용을 피한다. `@Getter`, `@NoArgsConstructor(access = PROTECTED)` 정도를 기본으로 하고 생성과 변경은 의미 있는 메서드로 제한한다.
- 기존 API·DB schema 호환성을 유지하며 작은 단계로 변경한다.

### 7.2 권장 순서

1. 이 문서와 `용어 정리.md`의 미확정 항목을 합의한다.
2. `ManagedDatabase` aggregate부터 생성·수정 불변식, credential 경계, 용어를 정렬한다.
3. `OperationJob`/`OperationTask`의 상태 전이 표를 코드와 테스트에 고정하고 cancel/retry/lease 규칙을 보완한다.
4. Configuration Profile을 aggregate root로 보고 parameter 규칙을 안으로 옮긴다.
5. Snapshot·Drift·Apply의 집계 무결성과 value type을 정렬한다.
6. Backup Verification의 Job/Task 연결과 cleanup 성공 정책을 확정한다.
7. 각 단계에서 도메인 테스트를 상태 전이·불변식 중심으로 재구성하고, application·adapter·API 테스트와 분리한다.
8. Lombok을 도입해 수동 getter·JPA 기본 생성자를 점진적으로 제거한다.

## 8. 확정이 필요한 질문

- 공식 한국어를 `관리 DB`로 할지 `DB 인스턴스`로 할지.
- Inventory의 활성 상태와 Health의 건강 상태 이름을 어떻게 분리할지.
- DB engine enum을 공유할지, 컨텍스트별로 변환할지.
- Job 취소의 허용 상태와 Agent Task 취소를 지원할지.
- Profile은 Active 상태에서 parameter 변경을 허용할지.
- Apply의 partial success를 운영적 성공으로 볼지, 실패로 볼지.
- 복원은 성공했지만 cleanup이 실패한 백업을 전체 성공으로 볼지.
- `LocalDateTime`을 유지할지 `Instant` 또는 offset 포함 시각으로 통일할지.
