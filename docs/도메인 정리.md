# DB FleetOps 도메인 정리

## 1. 문서의 목적과 상태

이 문서는 DB FleetOps의 요구사항과 도메인 모델을 같은 언어로 정렬하기 위한 기준 문서다. 현재 코드와 `docs` 아래의 설계 기록을 토대로 작성한 **현행 모델 초안**이며, 향후 도메인 합의에 따라 수정한다.

이 문서의 독자는 개발자로 한정하지 않는다. DB 운영자, 기획자, 정책·보안 담당자 등이 코드를 읽지 않고도 다음을 이해할 수 있어야 한다.

- FleetOps가 무엇을 관리하는지
- 각 정보가 왜 필요한지
- 사용자의 요청이 어떻게 실행되고 결과로 남는지
- 어떤 상태 변경이 허용되거나 금지되는지

문서와 코드가 다를 때의 우선순위는 다음과 같다.

1. 합의된 이 문서의 규칙과 용어
2. 실행 가능한 코드와 테스트로 확인된 현행 행위
3. 기존 `docs` 아래의 단계별 설계 기록

기존 개요·아키텍처 문서는 초기 Health/Inventory 단계를 설명하므로 현재 전체 범위를 대표하지 않는다.

## 2. 제품 정의

DB FleetOps는 여러 데이터베이스와 해당 호스트를 중앙에서 등록·관찰하고, 백업과 설정 점검·변경 같은 운영 작업을 안전하게 요청·실행·추적하는 DBMS 운영 관리 플랫폼이다.

쉽게 말하면, 운영자가 여러 DB 서버에 직접 접속해 같은 점검과 변경을 반복하는 대신 FleetOps가 대상·절차·결과를 한곳에서 관리하도록 돕는 시스템이다.

현재 제품은 다음 두 실행 영역으로 구성된다.

- **Control Plane(중앙 관리 영역)**: 관리 대상과 정책을 저장하고, 운영 작업의 순서와 상태를 조율하며, API와 운영자 화면을 제공한다.
- **Agent(현장 실행 프로그램)**: DB가 있는 서버 가까이에서 실행되며, 중앙에 할 일이 있는지 주기적으로 물어보고 미리 허용된 작업만 수행한다.

### 2.1 일을 처리하는 예시

운영자가 production DB의 백업과 복원 검증을 요청하는 경우를 예로 든다.

1. 운영자가 Console에서 관리 DB를 선택하고 백업을 요청한다.
2. Control Plane은 요청 전체를 추적할 `OperationJob`을 만든다.
3. Worker가 Job을 가져가고, Agent가 실행할 백업 `OperationTask`를 만든다.
4. Agent는 Task를 가져가 백업 파일을 만들고 결과를 보고한다.
5. 복원 검증이 요청되었다면 Agent가 임시 DB에 파일을 복원하고 table과 row를 확인한다.
6. Control Plane은 Job, Task, 복원 검증의 결과를 저장하고 운영자에게 최종 상태를 보여준다.

이처럼 Job은 “왜 하는가”와 전체 결과를, Task는 “현장에서 무엇을 실행하는가”를 나타낸다.

## 3. 전체 요구사항

### 3.1 관리 대상 DB

- 운영자는 관리 대상 DB 인스턴스를 등록·조회·수정·비활성화할 수 있어야 한다.
- DB 접속 정보와 자격 증명은 분리하고, 자격 증명은 API 응답에 노출하지 않아야 한다.
- 비활성 DB는 새로운 점검이나 운영 작업의 대상이 되어서는 안 된다.
- DBMS 종류에 따른 접속·진단·설정 차이는 Port/Adapter 경계 뒤로 격리한다.

### 3.2 건강 점검과 진단

- 시스템은 DB 연결 가능 여부와 응답 시간을 점검하고 결과를 남겨야 한다.
- 연결 실패는 인증 실패, 연결 거부, 시간 초과, 호스트 탐색 실패, 알 수 없는 오류로 분류한다.
- 운영자는 버전, uptime, 연결, 세션, 장기 트랜잭션, lock wait, slow query 정보를 조회할 수 있어야 한다.
- 진단은 임의 SQL 실행 기능이 아니라 제한된 진단 유스케이스로 제공한다.

### 3.3 Agent 관리

- Agent는 고유 token으로 등록하고 heartbeat를 보내야 한다.
- heartbeat를 수신한 Agent는 `ONLINE`이 되며, 관리자가 비활성화한 Agent는 heartbeat를 수신할 수 없다.
- Agent는 CPU·memory·disk 사용률과 수집 시각을 보고할 수 있어야 한다.
- Agent는 임의 명령이 아니라 미리 정의된 Task 종류만 실행한다.

### 3.4 운영 작업(Operation)

아래 내용은 `operation` 코드에 흩어진 현재 규칙을 요구사항의 문장으로 모은 초안이다.
클래스의 책임과 위치를 정하기 전에 먼저 이 규칙들이 실제 업무 요구사항으로 맞는지 확인한다.

#### 3.4.1 Job과 Task의 역할

- 시간이 걸리는 운영 요청은 즉시 처리하지 않고 `OperationJob`으로 접수한다.
- Job은 사용자가 요청한 전체 목적, 대상 DB, 요청자, 진행 상태와 최종 결과를 나타낸다.
- Task는 Agent가 현장에서 한 번에 실행할 수 있는 구체적인 작업을 나타낸다.
- Job과 Task는 서로 다른 생명주기와 실행권을 가지므로 별도 Aggregate로 관리한다.
- Job에 속한 Task는 `operationJobId`로 Job을 참조한다. Job과 무관한 독립 Task도 허용한다.
- 현재 Job 종류는 백업, 설정 점검, 설정 적용이다.
- 현재 Agent Task 종류는 Linux 상태 수집, MySQL 논리 백업, MySQL 복원 검증이다.

#### 3.4.2 Job 접수와 중복 방지

- Job은 존재하며 활성화된 관리 DB에 대해서만 생성할 수 있다.
- Job을 새로 만들면 최초 상태는 `QUEUED`, 재시도 횟수는 0, 최대 재시도 횟수는 3이다.
- 중복 방지 값이 있으면 대상 DB, Job 종류, 중복 방지 값이 모두 같은 기존 Job을 반환한다.
- 중복 방지 값이 없거나 공백이면 중복 여부를 판단하지 않고 새 Job을 만든다.
- 같은 중복 방지 조합의 Job은 DB에서도 하나만 저장되어야 한다.
- 설정 점검 Job에는 Profile ID와 요청자가 필요하다.
- 설정 적용 Job에는 Profile ID, 요청자와 한 개 이상의 변경 Parameter가 필요하다.
- 설정 적용 Job은 생성하기 전에 해당 설정을 적용할 수 있는지 설정 정책 영역에 확인해야 한다.
- Job 생성에 성공하면 생성 주체, Job ID와 대상 정보를 감사 기록으로 남긴다.

#### 3.4.3 Worker의 Job 가져오기

- Worker는 상태가 `QUEUED`이고 `availableAt`이 현재 시각보다 이르거나 같은 Job만 가져갈 수 있다.
- 실행 가능한 Job은 높은 우선순위가 먼저이며, 우선순위가 같으면 먼저 생성된 Job이 먼저다.
- 하나의 요청에서는 실행 가능한 Job 하나만 가져간다.
- 종료 중인 Worker는 새로운 Job을 가져오지 않는다. 조회 도중 종료가 시작된 경우에도 가져오기를 중단한다.
- Job을 가져오면 상태를 `RUNNING`으로 바꾸고 Worker ID와 Job 실행권 만료 시각을 기록한다.
- `QUEUED`가 아닌 Job은 시작할 수 없다.
- 가져오기와 상태 변경은 하나의 Transaction에서 처리하여 같은 Job의 중복 실행을 막아야 한다.
- Job을 가져오면 감사 기록을 남긴다.

#### 3.4.4 Job 종류별 실행

- 백업 Job을 가져오면 Agent가 실행할 `MYSQL_LOGICAL_BACKUP` Task를 만든다.
- 설정 점검 Job은 Worker가 설정 정책 영역에 실행을 요청하고, 설정 차이 결과를 받으면 Job을 성공 처리한다.
- 설정 점검 중 예외가 발생하면 Job을 실패 처리하며, 남은 재시도 횟수가 있으면 다시 대기시킨다.
- 설정 적용 Job은 Worker가 설정 정책 영역에 실행을 요청하고, 모든 적용 항목이 성공한 경우에만 Job을 성공 처리한다.
- 설정 적용 결과에 실패 또는 건너뜀 항목이 있거나 실행 중 예외가 발생하면 Job을 실패 처리하며 자동 재시도하지 않는다.
- Worker가 Job 성공이나 실패를 직접 보고할 때는 해당 Job이 `RUNNING`이고 요청 Worker가 현재 Job 실행권 소유자여야 한다.

#### 3.4.5 Job 상태와 재시도

- Job의 기본 흐름은 `QUEUED -> RUNNING -> SUCCEEDED | FAILED | TIMED_OUT`이다.
- 실행 중인 Job만 성공, 실패 또는 시간 초과로 종료할 수 있다.
- 성공한 Job은 다시 취소할 수 없다.
- 실패한 Job은 재시도 횟수가 최대값보다 작을 때만 `QUEUED`로 돌아갈 수 있다.
- 재대기된 Job은 재시도 횟수를 1 증가시키고 `availableAt` 이후에 다시 가져올 수 있다.
- 재대기할 때 이전 Worker와 Job 실행권 정보는 제거한다.
- 재시도할 수 없는 실패는 `FAILED`로 남는다.
- 성공, 실패, 재시도와 시간 초과 같은 중요한 상태 변경은 감사 기록으로 남긴다.

#### 3.4.6 Task 생성과 배정

- Task를 만들 때 실행할 Agent와 허용된 Task 종류가 반드시 있어야 한다.
- 존재하지 않는 Agent에는 Task를 배정할 수 없다.
- Job에 속한 Task는 Job ID를 가져야 한다.
- DB 접속이 필요한 백업·복원 Task에는 DB 접속 인증 정보 ID를 연결한다.
- 계정명과 비밀번호는 Task 실행 조건에 넣지 않는다.
- Task를 새로 만들면 최초 상태는 `QUEUED`, 실행 번호는 0이다.
- 백업 Task는 해당 Database에 명시적으로 배정된 Agent에게만 생성한다.
- 백업 Task 생성 시 Agent가 지정되지 않았거나 존재하지 않거나 `ONLINE`이 아니면 실행을 거절한다.
- 같은 Job에 같은 단계의 백업 Task가 이미 있으면 새 Task를 만들지 않고 기존 Task를 사용한다.

#### 3.4.7 Agent의 Task 가져오기와 실행권

- Agent는 자신의 ID와 Token이 유효할 때만 다음 Task를 요청할 수 있다.
- Agent는 Task 확인 요청을 보내고, 자신에게 배정된 `QUEUED` Task 중 가장 먼저 생성된 Task 하나를 가져간다.
- Task 조회, DB 잠금, `RUNNING` 전환, 실행 번호 증가와 Task 실행권 설정은 하나의 Transaction에서 처리한다.
- 처음 가져온 실행 번호는 1이며, 실행권 만료로 재대기된 Task를 다시 가져올 때마다 1 증가한다.
- Task를 가져오면 `startedAt`, `lastProgressAt`, `leaseExpiresAt`을 기록한다.
- 하나의 Task는 같은 시점에 한 Agent 실행만 소유할 수 있다.
- Task 실행권은 Task를 소유한 Agent가 현재 실행 번호로 요청할 때만 갱신할 수 있다.
- `RUNNING`이 아니거나 실행 번호가 다르거나 실행권이 이미 만료된 Task는 갱신할 수 없다.
- 갱신된 실행권 만료 시각은 현재 시각보다 뒤여야 하며, 갱신 성공 시 `lastProgressAt`도 함께 변경한다.
- Task 가져오기는 감사 기록으로 남긴다. 주기적인 실행권 갱신은 매번 감사 기록으로 저장하지 않는다.

#### 3.4.8 실행할 때 DB 접속 인증 정보 조회

- Agent는 Task를 가져온 뒤 실제 실행 직전에만 DB 접속 인증 정보를 조회할 수 있다.
- DB 접속 인증 정보 조회에는 유효한 Agent 인증 토큰, 해당 Agent 소유의 Task, 현재 실행 번호와 유효한 Task 실행권이 필요하다.
- Task는 DB 접속 인증 정보 ID를 가지고 있어야 한다.
- DB 접속 인증 정보가 연결된 관리 DB의 배정 Agent도 요청 Agent와 같아야 한다.
- 다른 Agent의 Task, 이전 실행 번호, 만료되거나 종료된 Task에서는 DB 접속 인증 정보를 받을 수 없다.
- 반환된 username과 password는 Task나 일반 Database 응답에 저장하거나 포함하지 않는다.

#### 3.4.9 Task 결과 보고와 멱등성

- 성공·실패 결과는 Task를 소유한 Agent가 유효한 Token으로 보고해야 한다.
- 최초 결과는 Task가 `RUNNING`이고 실행 번호가 현재 번호와 같으며 Task 실행권이 유효할 때만 접수한다.
- 성공 결과에는 Task 결과 내용, 실패 결과에는 오류 코드와 오류 메시지를 기록한다.
- 실패 결과에는 비어 있지 않은 오류 코드가 필요하다.
- 결과 보고마다 Agent가 만든 결과 보고 번호(`resultReportId`)와 결과 확인값(`resultReportFingerprint`)을 저장한다.
- 성공 결과 확인값은 결과 종류와 Task 결과 내용으로 계산하고, 실패 결과 확인값은 결과 종류, 오류 코드와 오류 메시지로 계산한다.
- 같은 실행 번호, 결과 보고 번호, 결과 종류와 결과 확인값의 재전송은 중복 보고로 인정하고 기존 결과를 반환한다.
- 중복 보고에서는 Metric 저장, Job 상태 변경과 후속 Task 생성을 다시 수행하지 않는다.
- 완료된 Task에 다른 실행 번호, 다른 결과 ID, 다른 결과 종류 또는 다른 내용을 보고하면 실행 충돌로 거절한다.
- Task 상태 충돌은 Operation 도메인 예외로 표현하고 Web Adapter가 HTTP 409로 변환한다.
- Task 결과 저장과 그 결과로 발생하는 Job 변경·Metric 저장·후속 Task 생성은 하나의 Transaction에서 함께 성공하거나 함께 취소되어야 한다.

#### 3.4.10 성공한 Task 결과의 후속 처리

- 처음 접수된 성공 결과만 Task 종류에 맞는 결과 처리기로 전달한다.
- Linux 상태 수집 Task의 성공 결과 내용은 Agent 영역에 전달하여 Host Metric으로 저장한다.
- MySQL 논리 백업이 성공하고 복원 검증이 필요하지 않으면 연결된 Job을 성공 처리한다.
- 복원 검증이 필요하면 같은 Job, Agent와 DB 접속 인증 정보를 사용하는 `MYSQL_RESTORE_VERIFY` Task를 하나만 만든다.
- MySQL 복원 검증 Task의 결과는 Backup Verification 영역에 기록한다.
- 복원 검증 결과가 통과하면 Job을 성공 처리하고, 통과하지 못하면 오류 코드와 메시지로 Job을 실패 처리한다.
- Agent가 Task 실행 자체를 실패로 보고하면 연결된 `RUNNING` Job도 실패 처리한다.
- Job과 연결되지 않은 독립 Task의 결과는 Job 상태를 변경하지 않는다.

#### 3.4.11 Job과 Task 상태 조정

- Task 실행권 갱신처럼 Task만 바뀌는 동작은 Job을 함께 잠그지 않는다.
- Task의 최종 결과를 Job에 반영할 때는 연결된 Job을 Lock으로 조회한다.
- 연결된 Task 중 `QUEUED` 또는 `RUNNING`이 하나라도 있으면 Job은 `RUNNING`을 유지한다.
- 진행 중 Task가 없고 `TIMED_OUT` Task가 하나라도 있으면 Job을 `TIMED_OUT`으로 종료한다.
- 진행 중 Task와 시간 초과 Task가 없고 `FAILED` Task가 하나라도 있으면 Job을 `FAILED`로 종료한다.
- 모든 Task가 종료됐는데 작업 흐름이 Job을 끝내지 않았다면 `JOB_WORKFLOW_INCONSISTENT` 오류로 Job을 실패 처리한다.
- 작업 흐름이 다음 Task 생성과 정상 성공을 판단하고, 공통 상태 조정 규칙은 실패·시간 초과·모순 상태를 판단한다.

#### 3.4.12 만료된 Task 회수

- 만료 검사기는 상태가 `RUNNING`이고 Task 실행권 만료 시각이 현재 시각보다 이르거나 같은 Task만 제한된 개수로 잠가 조회한다.
- 현재 실행 번호가 최대 실행 횟수보다 작으면 같은 Task ID를 `QUEUED`로 되돌린다.
- 재대기할 때 Task 실행권과 마지막 진행 시각은 비우되 실행 번호는 유지한다.
- 다시 가져올 때 같은 Task의 실행 번호가 증가하므로 이전 실행의 실행권 갱신과 결과 보고는 거절된다.
- 최대 실행 횟수에 도달한 Task는 `TASK_LEASE_EXPIRED` 오류와 함께 `TIMED_OUT`으로 종료한다.
- 최종 시간 초과 Task에 연결된 Job이 아직 `RUNNING`이면 Job도 시간 초과로 종료한다.
- Task 재대기와 최종 시간 초과는 감사 기록으로 남긴다.

#### 3.4.13 만료된 Job 조정

- 만료 검사기는 상태가 `RUNNING`이고 Job 실행권 만료 시각이 현재 시각보다 이르거나 같은 Job만 제한된 개수로 잠가 조회한다.
- 연결된 `QUEUED` 또는 `RUNNING` Task가 있으면 Agent 작업이 진행 중인 것으로 보고 Job을 재대기시키지 않는다.
- 진행 중 Task가 있는 만료 Job은 Job 실행권만 연장하며 새 Task를 만들지 않는다.
- 연결 Task가 하나도 없고 재시도 횟수가 남았으면 같은 Job을 `QUEUED`로 되돌린다.
- Task가 없는 Job을 재대기할 때 재시도 횟수를 늘리고 다음 실행 가능 시각을 설정한다.
- Task가 없는 Job이 최대 재시도 횟수에 도달하면 `JOB_LEASE_EXPIRED`로 `TIMED_OUT` 처리한다.
- 연결 Task가 모두 종료된 Job은 Task 상태 조정 규칙에 따라 실패, 시간 초과 또는 작업 흐름 불일치로 종료한다.
- Job 실행권 연장, 재대기, 시간 초과와 상태 조정은 감사 기록으로 남긴다.

#### 3.4.14 아직 합의하거나 보완해야 할 요구사항

다음 항목은 현재 코드에서 동작이 불완전하거나 업무 정책이 명확하지 않다. 따라서 위의 확정
요구사항과 구분하여 결정해야 한다.

- `maxRetryCount=3`이 최초 실행을 제외한 재시도 3회를 뜻하는지, 총 실행 3회를 뜻하는지 용어와 계산을 통일해야 한다.
- Worker의 성공·실패 보고는 Job 실행권 소유자만 확인하고 실행권 만료 여부는 확인하지 않는다. 실행권이 만료된 Worker의 늦은 보고를 허용할지 결정해야 한다.
- Job 실행권은 Job을 가져올 때 설정되지만 정상 실행 중 주기적으로 갱신하는 규칙이 없다. 긴 설정 점검·적용에서 필요한지 결정해야 한다.
- 일반 Task 생성은 전달받은 Job ID가 실제로 존재하는지 확인하지 않는다.
- Task의 `CANCELLED` 상태는 존재하지만 취소 행위와 전이 규칙이 없다.
- Job 취소는 성공 상태만 금지한다. 실패·시간 초과 Job도 취소할 수 있게 둘지 결정해야 한다.
- 결과 처리기를 찾지 못한 Task도 현재는 `SUCCEEDED`가 된다. 처리기가 반드시 필요한 Task와 결과 저장만 하면 되는 Task를 구분해야 한다.
- Task 실패 보고는 즉시 Job을 실패시키며 자동 재시도하지 않는다. 실행 오류에도 Task를 재시도할 조건이 필요한지 결정해야 한다.
- 백업 Task의 압축, 복원 검증, Row Count 검증과 정리 옵션이 현재 고정값이다. 사용자 요청값과 운영 Policy 중 어디에서 결정할지 정해야 한다.
- 복원 검증 실행 Task가 성공했더라도 검증 내용이 통과하지 않으면 Task는 `SUCCEEDED`, Job은 `FAILED`가 된다. 실행 성공과 업무 검증 실패를 이 상태 조합으로 표현할지 합의해야 한다.
- 모든 연결 Task가 성공했을 때 Job을 성공시키는 일반 규칙은 없다. 현재는 각 작업 흐름이 성공을 직접 결정하므로 새 Job 종류마다 종료 처리를 빠뜨릴 위험이 있다.
- `OperationJob` 일부 시간 계산은 주입된 `Clock`이 아니라 시스템 현재 시각을 직접 사용한다. 시간 경계 규칙을 일관되게 시험하려면 개선이 필요하다.

### 3.5 설정 정책과 설정 차이

- 설정 기준(`ConfigurationProfile`)은 DBMS·환경·버전 범위에 따른 기대 설정을 표현한다.
- 실제 설정 기록(`ConfigurationSnapshot`)은 특정 시점에 관리 DB에서 수집한 실제 설정을 표현한다.
- 설정 차이(`ConfigurationDrift`)는 같은 DBMS의 설정 기준과 실제 설정 기록을 비교한 결과다.
- 설정값은 `STRING`, `NUMBER`, `BOOLEAN` 규칙으로 비교하며 문자열 동등성만으로 판단하지 않는다.
- 설정 기준 항목은 필수 여부, 실행 중 변경 가능 여부, FleetOps 적용 허용 여부를 구분한다.

### 3.6 안전한 설정 적용

- 설정 변경은 설정 기준에 정의되고 FleetOps 적용이 허용된, 실행 중 변경 가능한 설정 항목만 대상으로 한다.
- 적용 전·후 실제 설정 기록을 남기고, 각 설정 항목의 요청값·이전값·결과값과 상태를 추적한다.
- 하나의 관리 DB에 대해 동시에 여러 설정 적용이 실행되지 않도록 한다.
- 일부 설정 항목만 성공한 경우를 전체 성공과 구분한다.

### 3.7 백업과 복원 검증

- logical backup은 파일 생성만으로 최종 성공이라고 판단하지 않는다.
- 복원 검증을 요청하면 임시 DB에 복원한 후 table 존재와 row count를 확인한다.
- 복원 성공과 임시 DB cleanup 성공을 구분해 기록한다.
- 대용량 DB의 표본 검증·성능 정책은 후속 설계 대상이다.

### 3.8 감사와 관측성

- 중요 운영 행위는 수행 주체, 행위, 대상, 결과, 메시지를 감사 기록으로 남겨야 한다.
- API와 Worker는 분리 실행할 수 있고, 작업 상태를 metric과 log로 관찰할 수 있어야 한다.

## 4. 바운디드 컨텍스트 초안

| 컨텍스트 | 책임 | 주요 모델 | 다른 컨텍스트와의 연결 |
|---|---|---|---|
| Inventory | 관리 DB와 DB 접속 인증 정보 관리 | ManagedDatabase, DatabaseCredential | 다른 모듈은 `databaseId`로 참조 |
| Health | DB 연결 상태와 운영 진단 | DatabaseHealthResult, 진단 값 | Inventory의 관리 DB와 DB 접속 인증 정보 사용 |
| Agent | 호스트 작업 실행 주체와 metric | Agent, AgentHostMetric | Task가 `agentId`로 지정 |
| Operation | 오래 걸리는 운영 요청을 작은 실행 단위로 나누고 순서·상태를 조정 | OperationJob, OperationTask | DB, Agent, Policy, Backup 조정 |
| Configuration Policy | Desired/Actual 설정 비교와 안전한 적용 | Profile, Snapshot, Drift, Apply | DB와 Job을 ID로 참조 |
| Backup Verification | 백업 산출물의 복원 가능성 검증 | BackupRestoreVerification, Item | Job과 Task를 ID로 참조 |
| Audit | 운영 행위 이력 | AuditLog | application port를 통해 기록 |

`policy`는 현재 하나의 패키지에 Profile·Snapshot·Drift·Apply를 모두 포함한다. 점진적 개선 중에는 일단 하나의 컨텍스트로 다루되, 규칙과 변경 빈도가 달라지면 분리를 재검토한다.

### 4.1 Operation Application의 의존 방향

Operation은 외부 Adapter와 Application Service 사이의 계약을 두 종류로 구분한다.

Operation은 먼저 업무 개념으로 나누고, 각 업무 모듈 안에서 의존 방향을 구분한다.

```text
operation
  ├─ job       Job 생성·선점·실행 결과 관리
  ├─ task      Agent 실행·실행권·결과 보고 관리
  ├─ workflow  Job과 Task의 실행 순서 조정
  └─ shared    여러 모듈이 함께 쓰는 외부 조회·감사 포트
```

각 업무 모듈 안의 기본 의존 방향은 다음과 같다.

```text
Adapter
  → application/provided
  → application/service
  → Domain
  → application/required
  ← Adapter
```

- `provided`는 Controller, Worker, Agent, Scheduler가 Operation에 요청할 수 있는 유스케이스다. 외부 Adapter는 구체 Service가 아니라 이 인터페이스를 사용한다.
- `required`는 Operation이 저장소, Agent, Inventory, Policy, Backup, Audit에 요청하는 기능이다. Application Service는 외부 Context의 Repository나 구현 Service를 직접 사용하지 않는다.
- 각 업무 모듈의 `adapter`가 인터페이스를 실제 기술과 연결한다.
  - `webapi`: HTTP 요청을 application의 provided 인터페이스로 전달한다.
  - `persistence`: required 저장 포트를 JPA Repository에 연결한다.
  - `integration`: Agent, Database, Audit 같은 다른 영역의 기능을 연결한다.
  - `scheduler`: 실행권이 만료된 Job과 Task를 주기적으로 확인한다.
  - `security`: DB 접속 인증 정보 조회와 비밀번호 복호화를 연결한다.
- required/provided에는 JPA, `Pageable` 같은 구현 기술 타입을 노출하지 않는다.

Job과 Task는 같은 Operation 안에 있지만 서로 다른 Aggregate로 유지한다. Task 실행권 갱신이
Job 전체를 잠그지 않게 하고, 최종 결과를 반영할 때만 `JobTaskCoordinator`가 둘을 조정한다.

Job과 Task는 Workflow 구현을 직접 참조하지 않는다. Task가 연결된 Job에 실패나 시간 초과를
알릴 때는 Task가 선언한 `LinkedJobProgress`를 사용하고, Workflow가 이를 구현한다. 따라서
`Job → Workflow → Task → Job` 같은 순환 의존이 생기지 않는다.

Task 결과 처리는 다음처럼 나뉜다.

```text
TaskReportService
  → Task 결과의 실행 번호와 중복 여부 확인
  → TaskResultDispatcher
  → Linux 상태 또는 백업 작업 흐름 처리
```

- Linux 상태값의 해석과 저장은 Agent 연결 Adapter가 담당한다.
- 백업 실행 조건과 복원 검증 결과의 해석은 Backup 영역이 담당한다.
- 설정 점검은 `ConfigurationCheck`를 통해 현재 DB 설정과 설정 기준의 비교 결과를 받는다.
- 설정 변경은 `ConfigurationChange`를 통해 요청값을 검사하고 DB에 적용한 결과를 받는다.
- Operation은 설정값을 직접 비교하거나 적용하지 않고, 반환된 결과로 Job 상태만 결정한다.
- Operation Application과 Domain은 다른 영역의 Entity, DTO, Repository를 직접 사용하지 않는다.

전체 도메인과 Operation 내부의 핵심 연결은
[유스케이스별 객체 의존 관계](diagram/유스케이스별-객체-관계.md)에 정리한다.

## 5. 도메인 모델의 속성과 행위

### 5.0 모델 분류 기준

| 분류 | 판단 기준 |
|---|---|
| Aggregate(집합) | 항상 같이 변경되어야 하는 도메인 객체의 묶음이다. 예를 들어 Apply와 각 Apply Item은 전체 결과 수가 항상 맞아야 하므로 하나의 집합으로 볼 수 있다. |
| Aggregate Root(집합 대표) | 집합 밖에서 직접 사용하는 대표 객체다. 외부는 구성원을 직접 바꾸지 않고 대표를 통해야 한다. 예: `ConfigurationApply`. |
| Entity(식별되는 개체) | 고유 식별자가 있어 속성이 변해도 같은 대상으로 추적한다. 이름이 바뀌어도 같은 관리 DB인 것과 같다. Aggregate Root도 Entity의 한 종류다. |
| Value Object(값 객체) | 고유 번호보다 값 자체가 중요하다. 예: “현재 연결 10개, 최대 100개”라는 연결 요약. 보통 생성 후 변경하지 않는다. |
| Domain Service(도메인 서비스) | 여러 개체를 함께 사용해야 해서 하나의 개체에 담기 어려운 업무 규칙을 수행한다. 예: Profile과 Snapshot의 설정값 비교. |

`생명주기`는 개체가 생성되고 상태가 바뀌며 종료되는 전체 과정을 뜻한다. `Repository`는 도메인 객체를 저장하고 다시 찾는 통로다. `불변식`은 어떤 상태에서도 반드시 지켜야 하는 규칙이다. 예를 들어 “완료된 Job은 다시 시작할 수 없다”는 불변식이다.

“현재 구현”에 나오는 `JPA Entity`는 DB table에 저장되는 Java 객체라는 뜻이다. `Java record`는 여러 값을 하나로 묶어 전달하는 간결한 Java 표현 방식이다. 이들은 코드가 현재 정보를 어떻게 저장·표현하는지 알려 주기 위한 기술 설명이며, 업무적 의미는 아래의 “도메인 분류”로 판단한다.

`@Entity`는 JPA 저장 방식을 나타낼 뿐 Aggregate Root임을 의미하지 않는다. 따라서 각 모델은 다음 두 관점으로 구분한다.

- **현재 구현**: JPA Entity, Java record 등 코드에서 확인되는 기술적 형태.
- **도메인 분류**: 현재 책임과 목표 aggregate 경계를 기준으로 한 DDD 역할. 경계 합의가 필요하면 `후보` 또는 `의도된 구성원`으로 표시한다.

### 5.1 Inventory

#### ManagedDatabase

- 의미: FleetOps가 관리하는 DB 인스턴스.
- 현재 구현: JPA Entity, 독립 Repository로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Inventory Aggregate의 진입점 후보다.

속성:

- `id`: 관리 DB의 고유 식별자.
- `name`: FleetOps에서 관리 DB를 구분하기 위한 표시 이름.
- `host`: DB에 접속할 호스트명 또는 IP 주소.
- `port`: DB가 연결을 수신하는 TCP port.
- `databaseName`: 접속할 논리 DB 이름.
- `engine`: DBMS 종류. 현재 `MYSQL`, `POSTGRESQL`을 표현한다.
- `status`: FleetOps의 관리 대상 여부. `ACTIVE` 또는 `INACTIVE`다.
- `environment`: DB가 속한 운영 환경. 예: production, staging.
- `serviceName`: DB를 사용하는 서비스의 이름.
- `owner`: DB의 관리 책임자 또는 책임 팀.
- `description`: DB에 대한 부가 설명.
- `createdAt`: 관리 DB가 등록된 시각.
- `updatedAt`: 관리 DB가 마지막으로 변경된 시각.

행위:

- `static register(RegisterManagedDatabaseRequest request)`: FleetOps에서 관리할 DB를 등록한다. 등록 요청과 필수 접속·관리 정보를 검증하고 상태를 `ACTIVE`로 초기화한다.
- `changeConnection(...)`: host, port, 논리 DB 이름, DBMS engine을 하나의 접속 정보 단위로 변경한다.
- `changeMetadata(...)`: 표시 이름, 운영 환경, 사용 서비스, 소유자, 설명을 관리 정보 단위로 변경한다.
- `deactivate()`: `ACTIVE` 상태를 `INACTIVE`로 변경하여 새 운영 작업의 대상에서 제외한다. 이미 비활성화된 DB에 다시 요청하면 거부한다.
- `requireActive()`: 연결 점검, 운영 진단, Job 생성 전에 `ACTIVE` 상태임을 보장한다. 비활성 DB면 요청을 차단한다.

불변식:

- `name`, `host`, `databaseName`, `environment`는 `null`, 빈 문자열, 공백만 있는 문자열일 수 없다.
- `port`는 1부터 65535 사이여야 한다.
- `engine`은 `null`일 수 없다.
- `serviceName`, `owner`, `description`은 부가 정보이므로 `null`을 허용한다.
- 잘못된 변경 요청은 검증이 완료되기 전에 거부하여 기존 정보를 부분적으로 변경하지 않는다.
- 접속 정보나 관리 정보가 변경되면 `updatedAt`을 갱신한다.
- 비활성화는 `ACTIVE -> INACTIVE`로만 전이할 수 있다. `INACTIVE -> INACTIVE`는 허용하지 않는다.

#### DatabaseCredential(DB 접속 인증 정보)

- 의미: 관리 DB에 접속하기 위한 자격 증명.
- 현재 구현: JPA Entity, `DatabaseCredentialRepository`로 독립 저장·조회.
- 도메인 분류: **Entity, ManagedDatabase Aggregate의 의도된 구성원**. 현재는 ID만으로 연결되고 Repository도 분리되어 실제 aggregate 경계는 코드에서 보장되지 않는다.

속성:

- `id`: DB 접속 인증 정보의 고유 식별자.
- `databaseId`: 이 인증 정보를 사용하는 관리 DB의 식별자.
- `username`: DB 인증에 사용할 계정명.
- `password`: DB 인증에 사용할 비밀번호.
- `createdAt`: DB 접속 인증 정보가 생성된 시각.
- `updatedAt`: DB 접속 인증 정보가 마지막으로 교체된 시각.

행위:

- `DatabaseCredential(...)`: 관리 DB의 계정명과 암호화된 비밀번호를 가진 DB 접속 인증 정보를 생성한다. 관리 DB 식별자와 빈 값이 아닌 계정명·비밀번호가 모두 필요하다.
- `changeCredentials(String username, String password)`: 계정명과 비밀번호를 하나의 인증 정보 단위로 교체하고 `updatedAt`을 변경한다. 두 값 중 하나라도 `null`, 빈 문자열, 공백만 있는 문자열이면 변경하지 않는다.

불변식:

- `databaseId`는 `null`일 수 없다.
- `username`과 `password`는 `null`, 빈 문자열, 공백만 있는 문자열일 수 없다.
- 잘못된 인증 정보 변경 요청은 기존 계정명과 비밀번호를 변경하지 않는다.

- 보안 보완 필요: 현재 password가 암호화나 secret reference 없이 저장되며 getter로 노출된다.

### 5.2 Health

#### DatabaseHealth

- 의미: 기본 DB 접속 점검의 즉시 결과 value.
- 현재 구현: Java record, JPA와 무관한 불변 객체.
- 도메인 분류: **Value Object**. 식별자나 별도 생명주기 없이 한 번의 접속 점검 결과를 값으로 표현한다.

속성:

- `databaseType`: 점검한 DBMS 종류의 문자열 표현.
- `host`: 점검한 DB host.
- `port`: 점검한 DB port.
- `status`: 연결 결과. `UP` 또는 `DOWN`이다.
- `latencyMs`: 연결 점검에 소요된 millisecond.
- `checkedAt`: 접속을 점검한 시각.
- `errorCode`: 접속 실패 분류. 성공 시 `null`이다.
- `message`: 점검 결과를 설명하는 메시지.

행위:

- `static up(...)`: 성공한 `UP` 접속 점검 결과를 생성한다.
- `static down(...)`: error code와 message를 포함한 `DOWN` 접속 점검 결과를 생성한다.

#### DatabaseHealthResult

- 의미: Inventory에 등록된 DB의 저장된 health check 결과.
- 현재 구현: JPA Entity, 독립 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity 후보**. 각 점검 결과가 독립적으로 저장되지만, 현재는 도메인 행위와 명시적 식별자 조회가 부족해 append-only 기록 모델에 가깝다.

속성:

- `id`: health check 결과의 고유 식별자. 현재 getter는 없다.
- `databaseId`: 점검한 관리 DB의 식별자.
- `status`: 판단된 건강 상태. `HEALTHY`, `DEGRADED`, `CRITICAL`, `UNKNOWN` 중 하나다.
- `connectionSuccess`: DB 연결 성공 여부.
- `responseTimeMs`: health check 응답 시간.
- `message`: health check 결과 설명.
- `checkedAt`: health check를 수행한 시각.

행위:

- `DatabaseHealthResult(...)`: 한 번의 health check 결과를 생성하고 `checkedAt`을 기록한다.

- 통합 필요: 두 모델이 상태·시간 타입·생성 규칙이 다르다. 기본 DB 점검을 Inventory 흐름으로 편입할지 결정해야 한다.

#### DatabaseVersionInfo

- 의미: 진단 대상 데이터베이스가 사용하는 DBMS 버전 정보다. 지원 여부나 기능 호환성을 판단하고, 장애를 분석할 때 해당 버전에 알려진 문제가 있는지 확인하는 기준이 된다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 특정 진단 시점에 DBMS가 응답한 버전을 불변 값으로 표현하며, 별도의 생명주기나 식별자를 갖지 않는다.

속성:

- `version`: DBMS가 보고한 제품 버전 문자열. 버전 번호뿐 아니라 DBMS 종류나 배포판 정보가 함께 포함될 수 있다.

행위:

- 별도의 도메인 메서드는 없다. 조회된 버전 정보를 변경하지 않고 전달한다.

#### DatabaseUptimeInfo

- 의미: 데이터베이스가 마지막으로 시작된 후 얼마나 오래 실행되고 있는지를 나타낸다. 값이 예상보다 짧다면 최근 재시작이나 장애 복구가 있었는지 확인하는 단서가 될 수 있다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 진단 시점의 가동 시간을 불변 값으로 표현하며, 가동 시간이 짧다는 사실만으로 장애를 의미하지는 않는다.

속성:

- `uptimeSeconds`: DBMS가 마지막으로 시작된 시점부터 진단 시점까지 경과한 시간(초).

행위:

- 별도의 도메인 메서드는 없다. 조회된 가동 시간을 변경하지 않고 전달한다.

#### ConnectionSummary

- 의미: 데이터베이스가 허용하는 연결 용량과 현재 사용 상황을 한눈에 보여주는 요약 정보다. 연결이 한계에 가까워지는 상황이나, 실제 작업 중인 연결이 비정상적으로 많은 상황을 파악하는 데 사용한다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 한 진단 시점의 연결 현황을 여러 수치의 묶음으로 표현한다.

속성:

- `currentConnections`: 현재 데이터베이스에 열려 있는 전체 연결 수. 작업 중인 연결뿐 아니라 대기 중인 연결도 포함할 수 있다.
- `runningConnections`: 현재 SQL 실행 등 실제 작업을 수행 중인 연결 수.
- `maxConnections`: DBMS 설정상 동시에 허용되는 최대 연결 수.
- `usagePercent`: 최대 연결 수 대비 현재 연결 수의 사용 비율. 연결 용량이 얼마나 남았는지 판단하는 지표다.

행위:

- 별도의 도메인 메서드는 없다. 조회 시점의 연결 현황을 변경하지 않고 전달한다.

#### SessionInfo

- 의미: 데이터베이스에 접속한 개별 세션 하나의 현재 상태를 나타낸다. 어떤 사용자가 어디에서 접속했고, 무엇을 얼마나 오래 수행하고 있는지 확인할 때 사용한다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 진단 시점에 관찰된 세션 상태를 불변 값으로 표현한다. 세션 자체를 관리하는 Entity가 아니라 조회 결과다.

속성:

- `processId`: DBMS가 해당 세션 또는 프로세스에 부여한 식별자. 문제 세션을 구분할 때 사용한다.
- `user`: 세션이 데이터베이스 접속에 사용한 계정 이름.
- `host`: 세션을 생성한 클라이언트의 호스트 정보. 접속한 서버나 장비를 추적하는 데 사용한다.
- `databaseName`: 세션이 현재 선택하여 사용 중인 데이터베이스 이름.
- `command`: 세션이 현재 수행 중인 작업 종류. SQL 실행, 대기 등 DBMS가 분류한 명령을 나타낸다.
- `timeSeconds`: 현재 명령 또는 상태가 지속된 시간(초).
- `state`: DBMS가 보고한 세션의 세부 실행 상태.
- `queryPreview`: 세션이 실행 중인 SQL을 화면에서 빠르게 확인할 수 있도록 길이를 제한한 미리보기. 전체 SQL이 아닐 수 있다.

행위:

- 별도의 도메인 메서드는 없다. 조회 시점의 세션 상태를 변경하지 않고 전달한다.

#### LongTransactionInfo

- 의미: 일정 시간 이상 끝나지 않고 유지되는 트랜잭션의 상태를 나타낸다. 장기 트랜잭션은 잠금이나 자원을 오래 점유하여 다른 작업에 영향을 줄 수 있으므로 원인을 확인하는 데 사용한다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 진단 시점에 장기 실행 중인 트랜잭션을 관찰한 결과이며, 트랜잭션 자체의 생명주기를 관리하지 않는다.

속성:

- `transactionId`: DBMS가 해당 트랜잭션에 부여한 식별자.
- `state`: DBMS가 보고한 트랜잭션의 현재 상태.
- `startedAt`: 트랜잭션이 시작된 시각.
- `durationSeconds`: 트랜잭션이 시작된 후 진단 시점까지 지속된 시간(초).
- `threadId`: 트랜잭션을 수행 중인 DBMS 스레드 또는 세션의 식별자.
- `queryPreview`: 트랜잭션에서 수행 중인 SQL을 확인하기 위한 제한된 미리보기. 전체 SQL이 아닐 수 있다.

행위:

- 별도의 도메인 메서드는 없다. 조회된 장기 트랜잭션 상태를 변경하지 않고 전달한다.

#### LockWaitInfo

- 의미: 한 트랜잭션이 필요한 데이터 잠금을 얻지 못해 다른 트랜잭션의 작업 종료를 기다리는 관계를 나타낸다. 기다리는 쪽과 잠금을 점유한 쪽을 함께 보여주어 지연 원인을 찾는 데 사용한다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 진단 시점에 관찰된 잠금 대기 관계를 불변 값으로 표현하며, 두 트랜잭션 자체를 관리하지 않는다.

속성:

- `waitingTransactionId`: 잠금을 얻지 못해 대기 중인 트랜잭션의 식별자.
- `waitingThreadId`: 대기 중인 트랜잭션을 수행하는 DBMS 스레드 또는 세션의 식별자.
- `waitingQueryPreview`: 잠금을 기다리고 있는 SQL의 제한된 미리보기.
- `blockingTransactionId`: 필요한 잠금을 현재 점유하여 다른 작업을 기다리게 하는 트랜잭션의 식별자.
- `blockingThreadId`: 잠금을 점유한 트랜잭션을 수행하는 DBMS 스레드 또는 세션의 식별자.
- `blockingQueryPreview`: 잠금을 점유하고 있는 SQL의 제한된 미리보기.

행위:

- 별도의 도메인 메서드는 없다. 조회된 잠금 대기 관계를 변경하지 않고 전달한다.

#### SlowQueryInfo

- 의미: 같은 형태의 SQL을 하나의 유형으로 묶어 실행 성능을 요약한 정보다. 자주 실행되거나 평균·최대 실행 시간이 긴 SQL 유형을 찾아 개선 우선순위를 정하는 데 사용한다.
- 현재 구현: Java `record`.
- 도메인 분류: **Value Object**. 일정 기간 동안 집계된 SQL 유형의 성능 통계를 불변 값으로 표현한다. 개별 SQL 실행 한 건을 의미하지 않는다.

속성:

- `digestText`: 값이 달라도 구조가 같은 SQL을 함께 집계할 수 있도록 정규화한 SQL 문장. 실제 실행된 원문과 다를 수 있다.
- `executionCount`: 해당 SQL 유형이 집계 기간 동안 실행된 횟수.
- `averageSeconds`: 해당 SQL 유형 한 건의 평균 실행 시간(초).
- `maxSeconds`: 해당 SQL 유형에서 관찰된 가장 긴 실행 시간(초).
- `rowsExamined`: 결과를 찾기 위해 DBMS가 검사한 행 수. 반환 행 수에 비해 지나치게 크면 비효율적인 조회의 단서가 될 수 있다.
- `rowsSent`: DBMS가 클라이언트에 실제로 반환한 행 수.

행위:

- 별도의 도메인 메서드는 없다. 집계된 느린 SQL 통계를 변경하지 않고 전달한다.

### 5.3 Agent

#### Agent

- 의미: Control Plane에 등록된 호스트 작업 실행자.
- 현재 구현: JPA Entity, 독립 Repository로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Agent 등록·인증·상태 생명주기의 진입점이다.

속성:

- `id`: Agent의 고유 식별자.
- `agentName`: Control Plane에서 Agent를 구분하는 이름.
- `hostname`: Agent가 실행되는 host의 hostname.
- `ipAddress`: Agent host의 IP 주소.
- `osName`: Agent host의 운영체제 이름.
- `architecture`: Agent binary가 실행되는 CPU architecture. 빈 값은 `unknown`으로 정규화한다.
- `agentVersion`: 실행 중인 Agent software 버전.
- `agentToken`: Agent 인증에 사용하는 token.
- `status`: `ONLINE`, `OFFLINE`, `UNKNOWN`, `DISABLED` 중 하나인 Agent 상태.
- `lastHeartbeatAt`: 마지막 heartbeat를 수신한 시각.
- `createdAt`: Agent가 등록된 시각.
- `updatedAt`: Agent 상태가 마지막으로 변경된 시각.

행위:

- `static register(...)`: Agent를 등록하고 `ONLINE`으로 초기화한다. architecture를 받는 형태와 `unknown`을 사용하는 형태가 있다.
- `recordHeartbeat()`: heartbeat 수신 사실을 기록한다. 비활성화된 Agent가 아니면 `ONLINE`으로 변경하고 heartbeat/수정 시각을 갱신한다.
- `markOffline()`: Agent를 `OFFLINE`으로 변경한다. 비활성화됐거나 이미 offline인 Agent에는 사용할 수 없다.
- `disable()`: Agent를 `DISABLED`로 변경한다. 이미 비활성화된 Agent에는 다시 사용할 수 없다.
- `matchesToken(String token)`: 제공된 token과 Agent token의 일치 여부를 판단한다.

- 규칙: 등록에 필요한 문자열은 null이거나 공백일 수 없으며 architecture만 빈 값이면 `unknown`으로 정규화한다. 등록 시 상태는 `ONLINE`이다. 비활성화된 Agent는 heartbeat 기록과 offline 전환을 할 수 없고, 같은 상태로 중복 비활성화하거나 offline 전환할 수 없다.

#### AgentHostMetric

- 의미: Agent host의 한 시점 자원 사용률.
- 현재 구현: JPA Entity, 독립 Repository로 저장.
- 도메인 분류: **Entity, Agent Aggregate의 의도된 구성원**. 시계열 metric을 Agent Aggregate 안에 포함할지 별도 Metric Aggregate로 다룰지는 저장량과 생명주기를 기준으로 추가 확정해야 한다.

속성:

- `id`: host metric의 고유 식별자.
- `agentId`: metric을 보고한 Agent의 식별자.
- `cpuUsagePercent`: CPU 사용률.
- `memoryUsagePercent`: memory 사용률.
- `diskUsagePercent`: disk 사용률.
- `collectedAt`: Agent가 metric을 수집한 시각.

행위:

- `static create(...)`: Agent의 CPU, memory, disk 사용률과 수집 시각을 가진 metric을 생성한다.

- 보완 필요: 사용률의 0~100 범위를 검증하지 않는다.

### 5.4 Operation

#### OperationJob

- 의미: 사용자가 요청한 하나의 운영 목적과 전체 실행 결과.
- 현재 구현: JPA Entity, 독립 Repository로 저장. optimistic locking(두 Worker가 같은 Job을 동시에 변경하는 것을 감지하는 방식)을 사용한다.
- 도메인 분류: **Aggregate Root / Entity**. 운영 요청의 전체 생명주기와 결과를 책임진다.

속성:

- `id`: Job의 고유 식별자.
- `jobType`: 운영 목적. 현재 `BACKUP`, `CONFIGURATION_CHECK`, `CONFIGURATION_APPLY` 중 하나다.

`RESTART` Job과 `CONFIGURATION_CHECK` Task는 실제 실행 경로가 없어 제거했다. 배포 전 기존
Database에 사용 중인 값이 없는지 다음 조회로 확인한다.

```sql
SELECT COUNT(*) FROM operation_job WHERE job_type = 'RESTART';
SELECT COUNT(*) FROM operation_task WHERE task_type = 'CONFIGURATION_CHECK';
```

조회 결과가 0이 아니라면 해당 작업을 먼저 종료하거나 정리한 뒤 배포한다.
- `targetDatabaseId`: Job이 대상으로 하는 관리 DB 식별자.
- `status`: Job의 현재 생명주기 상태.
- `requestedBy`: Job을 요청한 사용자 또는 시스템.
- `idempotencyKey`: 동일한 Job의 중복 생성을 막는 중복 방지 값.
- `requestPayload`: Job 종류별 요청 조건을 담은 JSON 문자열.
- `priority`: Job 실행 우선순위. 현재 기본값은 0이다.
- `retryCount`: 이미 수행한 재시도 횟수.
- `maxRetryCount`: 허용된 최대 재시도 횟수. 현재 기본값은 3이다.
- `leaseOwner`: Job 실행권을 가진 Worker의 식별자.
- `leaseUntil`: Worker의 Job 실행권이 만료되는 시각.
- `availableAt`: Worker가 Job을 가져갈 수 있게 되는 시각.
- `startedAt`: Job 실행이 시작된 시각.
- `finishedAt`: Job이 종료 상태에 도달한 시각.
- `resultCode`: Job 결과를 분류하는 code.
- `resultMessage`: Job 결과의 상세 설명.
- `version`: 동시 변경을 감지하기 위한 optimistic-lock version.
- `createdAt`: Job이 생성된 시각.
- `updatedAt`: Job이 마지막으로 변경된 시각.

행위:

- `static create(...)`: `QUEUED` 상태의 Job을 생성한다. Job 요청 내용을 받는 형태도 있다.
- `start(String workerId, LocalDateTime leaseUntil)`: `QUEUED` Job을 `RUNNING`으로 변경하고 Job 실행권을 설정한다.
- `succeed(String resultMessage)`: `RUNNING` Job을 `SUCCEEDED`로 종료한다.
- `fail(String resultCode, String resultMessage)`: `RUNNING` Job을 `FAILED`로 종료한다.
- `retry(LocalDateTime nextAvailableAt)`: 재시도 횟수가 남은 `FAILED` Job을 `QUEUED`로 돌리고 다음 실행 가능 시각을 설정한다.
- `cancel()`: 성공하지 않았고 이미 취소되지 않은 Job을 `CANCELLED`로 종료한다.
- `timeout()`: `RUNNING` Job을 `TIMED_OUT`로 종료한다.

- 상태 전이: `QUEUED -> RUNNING -> SUCCEEDED|FAILED|TIMED_OUT`; `FAILED -> QUEUED`; `QUEUED|RUNNING|FAILED|TIMED_OUT -> CANCELLED`. 허용되지 않는 상태 전이는 예외로 거부한다. 현재 `FAILED` Job을 cancel할 수 있는 점은 정책 확정이 필요하다.

#### OperationTask

- 의미: Agent가 수행하는 구체적인 실행 단위.
- 현재 구현: JPA Entity, 독립 Repository·API·생명주기로 저장·조회.
- 도메인 분류: **Aggregate Root / Entity**. Job을 ID로 참조하지만 Agent와 독립적으로 상태를 변경하므로 별도 Aggregate로 다루는 것이 현재 구조에 부합한다.

속성:

- `id`: Task의 고유 식별자.
- `agentId`: Task를 실행할 Agent 식별자.
- `operationJobId`: Task를 생성한 Job 식별자. 독립 Task는 `null`일 수 있다.
- `taskType`: Agent가 실행할 허용된 작업 종류.
- `status`: Task의 현재 생명주기 상태.
- `parametersJson`: Task 실행 parameter를 담은 JSON 문자열.
- `resultPayloadJson`: Task가 반환한 구조화된 결과 내용.
- `errorCode`: Task 실패 분류 code.
- `errorMessage`: Task 실패의 상세 설명.
- `startedAt`: Agent가 Task 실행을 시작한 시각.
- `completedAt`: Task가 성공 또는 실패로 종료된 시각.
- `createdAt`: Task가 생성된 시각.
- `updatedAt`: Task가 마지막으로 변경된 시각.

행위:

- `static create(...)`: Job과 연결되지 않은 `QUEUED` Task를 생성한다.
- `static createForJob(...)`: 특정 Job에 속한 `QUEUED` Task를 생성한다.
- `start()`: `QUEUED` Task를 `RUNNING`으로 변경한다.
- `succeed(String resultPayloadJson)`: `RUNNING` Task에 결과 내용을 기록하고 `SUCCEEDED`로 성공 처리한다.
- `fail(String errorCode, String errorMessage)`: `RUNNING` Task에 실패 정보를 기록하고 `FAILED`로 종료한다.

- 규칙: Agent 식별자와 작업 유형은 필수다. Job에 속한 Task에는 Operation Job 식별자가 필요하며, 실패 처리에는 오류 코드가 필요하다.
- 상태 전이: `QUEUED -> RUNNING -> SUCCEEDED|FAILED`. 허용되지 않는 상태 전이는 예외로 거부한다.
- 불일치: enum에 `CANCELLED`가 있지만 현재 도메인 행위로는 전이할 수 없다.

### 5.5 Configuration Policy

#### ConfigurationProfile(설정 기준)

- 의미: 특정 DBMS·환경·버전 범위에 적용할 Desired State의 헤더.
- 현재 구현: JPA Entity, Parameter와 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. Profile의 생명주기와 Parameter 규칙을 책임지는 Configuration Profile Aggregate의 진입점이다.

속성:

- `id`: Profile의 고유 식별자.
- `profileName`: Profile을 구분하는 이름.
- `engineType`: Profile이 대상으로 하는 DBMS 종류.
- `environment`: Profile을 적용할 운영 환경.
- `versionRange`: Profile과 호환되는 DBMS 버전 범위.
- `description`: Profile의 목적과 적용 기준에 대한 설명.
- `status`: Profile 생명주기 상태. `DRAFT`, `ACTIVE`, `INACTIVE` 중 하나다.
- `createdAt`: Profile이 생성된 시각.
- `updatedAt`: Profile이 마지막으로 변경된 시각.

행위:

- `static create(...)`: `DRAFT` 상태의 Profile을 생성한다.
- `activate()`: Profile을 `ACTIVE`로 변경한다.
- `deactivate()`: Profile을 `INACTIVE`로 변경한다.
- `updateDescription(String description)`: Profile 설명을 수정한다.

#### ConfigurationProfileParameter(설정 기준 항목)

- 의미: Profile이 정의한 하나의 DBMS parameter 규칙.
- 현재 구현: JPA Entity, Profile과 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationProfile Aggregate의 의도된 구성원**. 현재는 Profile ID만 보유하며 Aggregate Root가 집합 규칙을 직접 보장하지 못한다.

속성:

- `id`: Profile Parameter의 고유 식별자.
- `profileId`: Parameter가 속한 Profile 식별자.
- `parameterName`: DBMS parameter 이름.
- `expectedValue`: Desired State에서 기대하는 parameter 값.
- `valueType`: 값 비교와 검증에 사용할 `STRING`, `NUMBER`, `BOOLEAN` 타입.
- `required`: Actual State에 parameter가 반드시 존재해야 하는지의 여부.
- `dynamic`: DB 재시작 없이 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 parameter를 직접 변경해도 되는지의 여부.
- `description`: Parameter의 의미와 정책에 대한 설명.
- `createdAt`: Parameter 규칙이 생성된 시각.
- `updatedAt`: Parameter 규칙이 마지막으로 변경된 시각.

행위:

- `static create(...)`: Profile에 속한 Parameter 규칙을 생성한다. nullable boolean에는 required `true`, dynamic/applyAllowed `false`를 기본값으로 적용한다.
- `updateExpectedValue(String expectedValue, ParameterValueType valueType)`: 기대값과 값 타입을 함께 수정한다.
- `updateApplyPolicy(Boolean dynamic, Boolean applyAllowed)`: 동적 변경 가능 여부와 FleetOps 적용 허용 여부를 수정한다.

- 집합 규칙 보완 필요: Profile이 parameter 집합을 소유하지 않고 Service가 별도 Repository로 조정한다. Active Profile 수정 가능 여부도 확정해야 한다.

#### ConfigurationSnapshot(실제 설정 기록)

- 의미: 특정 시점의 DB Actual State 헤더.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 한 번 수집된 Actual State 집합의 진입점이다.

속성:

- `id`: Snapshot의 고유 식별자.
- `databaseId`: 설정을 수집한 관리 DB 식별자.
- `engineType`: 수집 대상 DBMS 종류.
- `capturedAt`: DB 설정을 수집한 시각.

행위:

- `static create(Long databaseId, ConfigurationEngineType engineType)`: DB와 engine을 기준으로 Snapshot 헤더를 생성한다.

#### ConfigurationSnapshotItem(실제 설정 항목)

- 의미: Snapshot에 수집된 하나의 DBMS parameter 값.
- 현재 구현: JPA Entity, Snapshot과 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationSnapshot Aggregate의 의도된 구성원**. 식별자를 가지지만 Snapshot 생성 후에는 변경하지 않는다.

속성:

- `id`: Snapshot Item의 고유 식별자.
- `snapshotId`: Item이 속한 Snapshot 식별자.
- `parameterName`: 수집한 DBMS parameter 이름.
- `actualValue`: 수집 시점의 실제 parameter 값.
- `unit`: parameter 값의 단위.
- `valueType`: DBMS 또는 Adapter가 보고한 값 타입의 문자열 표현.
- `dynamic`: 수집된 parameter가 동적 변경 가능한지의 여부.
- `source`: parameter 값을 얻은 DBMS view·command 등의 출처.
- `createdAt`: Snapshot Item이 저장된 시각.

행위:

- `static create(...)`: Snapshot에 속한 하나의 Actual State Item을 생성한다.

- 타입 불일치: Item의 `valueType`이 enum이 아닌 String이다.

#### ConfigurationDrift(설정 차이)

- 의미: Profile과 Snapshot을 비교한 전체 결과.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 하나의 비교 실행과 parameter별 결과 집합을 대표한다.

속성:

- `id`: Drift 결과의 고유 식별자.
- `databaseId`: 비교 대상 관리 DB 식별자.
- `profileId`: Desired State로 사용한 Profile 식별자.
- `snapshotId`: Actual State로 사용한 Snapshot 식별자.
- `engineType`: 비교 대상 DBMS 종류.
- `status`: 전체 비교 결과. `COMPLIANT` 또는 `NON_COMPLIANT`다.
- `totalCount`: 비교한 전체 parameter 수.
- `compliantCount`: 기대값과 일치한 parameter 수.
- `nonCompliantCount`: 존재하지만 기대값과 다른 parameter 수.
- `missingCount`: Actual State에서 찾을 수 없는 parameter 수.
- `checkedAt`: Profile과 Snapshot을 비교한 시각.

행위:

- `static create(...)`: 비교 상태와 parameter별 집계를 가진 Drift 결과를 생성한다.

#### ConfigurationDriftItem(설정 차이 항목)

- 의미: 하나의 parameter에 대한 Desired/Actual State 비교 결과.
- 현재 구현: JPA Entity, Drift와 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationDrift Aggregate의 의도된 구성원**. 결과 생성 후에는 변경하지 않는다.

속성:

- `id`: Drift Item의 고유 식별자.
- `driftId`: Item이 속한 Drift 식별자.
- `parameterName`: 비교한 DBMS parameter 이름.
- `expectedValue`: Profile이 정의한 기대값.
- `actualValue`: Snapshot에서 확인한 실제값.
- `valueType`: 비교 규칙에 사용한 값 타입.
- `required`: parameter가 Actual State에 반드시 있어야 하는지의 여부.
- `dynamic`: parameter가 동적으로 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 parameter를 변경해도 되는지의 여부.
- `complianceStatus`: `COMPLIANT`, `NON_COMPLIANT`, `MISSING` 중 하나인 비교 결과.
- `message`: 해당 비교 결과의 상세 설명.
- `createdAt`: Drift Item이 생성된 시각.

행위:

- `static create(...)`: parameter 하나의 비교 결과를 생성한다.

- 현재 행위는 결과 생성만 있고, 집계 무결성은 생성자 밖 Service에서 보장한다.

#### ConfigurationApply(설정 적용)

- 의미: 관리 DB에 설정 변경을 적용하는 전체 운영 행위와 결과.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. Apply 생명주기, 전·후 Snapshot, parameter 결과 집계를 책임진다.

속성:

- `id`: Apply의 고유 식별자.
- `databaseId`: 설정을 변경할 관리 DB 식별자.
- `operationJobId`: Apply의 실행 순서와 상태를 조정하는 Job 식별자.
- `requestedBy`: Apply를 요청한 사용자 또는 시스템.
- `reason`: 설정 변경을 요청한 이유.
- `status`: `REQUESTED`, `RUNNING`, `SUCCEEDED`, `PARTIALLY_SUCCEEDED`, `FAILED`, `CANCELLED` 중 하나인 Apply 상태.
- `totalCount`: 적용 대상 parameter 전체 수.
- `successCount`: 적용과 검증에 성공한 parameter 수.
- `failedCount`: 적용 또는 검증에 실패한 parameter 수.
- `skippedCount`: 정책상 적용하지 않은 parameter 수.
- `beforeSnapshotId`: Apply 시작 전에 수집한 Snapshot 식별자.
- `afterSnapshotId`: Apply 완료 후에 수집한 Snapshot 식별자.
- `createdAt`: Apply 요청이 생성된 시각.
- `startedAt`: Apply 실행이 시작된 시각.
- `completedAt`: Apply가 종료 상태에 도달한 시각.

행위:

- `static create(...)`: `REQUESTED` 상태의 Apply를 생성하고 count를 초기화한다.
- `start(Long beforeSnapshotId)`: before Snapshot을 연결하고 `REQUESTED`를 `RUNNING`으로 변경한다.
- `complete(...)`: after Snapshot과 결과 count를 기록하고 `SUCCEEDED`, `PARTIALLY_SUCCEEDED`, `FAILED` 중 하나로 종료한다.
- `fail(...)`: 현재까지의 결과 count를 기록하고 `FAILED` 또는 `PARTIALLY_SUCCEEDED`로 종료한다.
- `cancel()`: 완료 상태가 아닌 Apply를 `CANCELLED`로 종료한다.

#### ConfigurationApplyItem(설정 적용 항목)

- 의미: Apply에서 하나의 parameter에 수행한 변경과 검증 결과.
- 현재 구현: JPA Entity, Apply와 분리된 Repository로 저장.
- 도메인 분류: **Entity, ConfigurationApply Aggregate의 의도된 구성원**. Parameter 단위 생명주기를 가지지만 전체 집계는 Apply Root가 보장해야 한다.

속성:

- `id`: Apply Item의 고유 식별자.
- `applyId`: Item이 속한 Apply 식별자.
- `parameterName`: 변경할 DBMS parameter 이름.
- `requestedValue`: DB에 적용하려는 값.
- `beforeValue`: 적용 전에 수집한 parameter 값.
- `afterValue`: 적용 후에 수집하여 검증한 parameter 값.
- `valueType`: parameter 값의 검증·비교 타입.
- `dynamic`: DB 재시작 없이 변경 가능한지의 여부.
- `applyAllowed`: FleetOps가 변경해도 되는지의 여부.
- `applyStatus`: `PENDING`, `APPLIED`, `VERIFIED`, `SKIPPED`, `FAILED`, `UNSUPPORTED` 중 하나인 Item 상태.
- `failureCode`: 미적용 또는 실패 이유를 분류하는 code.
- `failureMessage`: 미적용 또는 실패의 상세 설명.
- `createdAt`: Apply Item이 생성된 시각.
- `appliedAt`: DB에 변경을 적용한 시각.
- `verifiedAt`: 적용 후 값을 검증한 시각.

행위:

- `static create(...)`: `PENDING` 상태의 parameter Apply Item을 생성한다.
- `markBeforeValue(String beforeValue)`: 변경 전 parameter 값을 기록한다.
- `markApplied()`: `PENDING` Item을 `APPLIED`로 변경하고 적용 시각을 기록한다.
- `markVerified(String afterValue)`: `APPLIED` Item에 변경 후 값을 기록하고 `VERIFIED`로 변경한다.
- `markSkipped(String failureCode, String failureMessage)`: Item을 `SKIPPED`로 종료하고 이유를 기록한다.
- `markUnsupported(String failureCode, String failureMessage)`: Item을 `UNSUPPORTED`로 종료하고 이유를 기록한다.
- `markFailed(String failureCode, String failureMessage)`: Item을 `FAILED`로 종료하고 실패 정보를 기록한다.

- Item 전이는 `PENDING -> APPLIED -> VERIFIED`이며 `SKIPPED|UNSUPPORTED|FAILED`로도 종료할 수 있다.
- 무결성 보완 필요: count 합계와 total의 일치, 음수 금지, `fail()`의 허용 이전 상태, Item의 종료 상태 재변경 금지가 완전히 보장되지 않는다.

### 5.6 Backup Verification

#### BackupRestoreVerification(복원 검증)

- 의미: 백업 산출물을 임시 DB에 복원하여 사용 가능성을 확인하는 전체 검증.
- 현재 구현: JPA Entity, Item과 분리된 Repository로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 복원 검증 생명주기와 table별 결과 집계를 대표한다.

속성:

- `id`: Restore Verification의 고유 식별자.
- `operationJobId`: 백업과 복원 검증을 요청한 Job 식별자.
- `backupTaskId`: 백업 파일을 생성한 Task 식별자.
- `restoreVerifyTaskId`: 복원 검증을 실행한 Task 식별자.
- `databaseId`: 백업 원본인 관리 DB 식별자.
- `sourceDatabaseName`: 백업한 원본 논리 DB 이름.
- `backupFile`: 검증할 백업 파일의 경로 또는 식별 정보.
- `temporaryDatabaseName`: 복원 검증에 사용할 임시 DB 이름.
- `status`: `REQUESTED`, `RUNNING`, `VERIFIED`, `FAILED`, `CLEANUP_FAILED` 중 하나인 검증 상태.
- `restoredTableCount`: 임시 DB에 복원된 table 수.
- `checkedTableCount`: 존재와 row count를 확인한 table 수.
- `totalRowCount`: 검증한 table의 row count 합계.
- `errorCode`: 복원·검증·cleanup 실패 분류 code.
- `errorMessage`: 복원·검증·cleanup 실패의 상세 설명.
- `startedAt`: 복원 검증을 시작한 시각.
- `completedAt`: 검증이 종료 상태에 도달한 시각.
- `createdAt`: 검증 요청이 생성된 시각.

행위:

- `static create(...)`: 백업·복원 Task와 검증 대상을 연결하고 `REQUESTED`로 초기화한다.
- `start()`: `REQUESTED` 검증을 `RUNNING`으로 변경한다.
- `verify(...)`: `RUNNING` 검증에 table/row 집계를 기록하고 `VERIFIED`로 종료한다.
- `fail(String errorCode, String errorMessage)`: 검증을 `FAILED`로 종료하고 실패 정보를 기록한다. `VERIFIED`에서는 허용하지 않는다.
- `cleanupFailed(String errorCode, String errorMessage)`: `RUNNING` 또는 `VERIFIED` 검증을 `CLEANUP_FAILED`로 변경한다.

- 전이는 `REQUESTED -> RUNNING -> VERIFIED|FAILED|CLEANUP_FAILED`, 또는 `VERIFIED -> CLEANUP_FAILED`다.

#### BackupRestoreVerificationItem(복원 검증 항목)

- 의미: 복원된 table 하나의 검증 결과.
- 현재 구현: JPA Entity, Verification과 분리된 Repository로 저장.
- 도메인 분류: **Entity, BackupRestoreVerification Aggregate의 의도된 구성원**. 식별자를 가지고 table별 결과로 추적되며 생성 후에는 변경하지 않는다.

속성:

- `id`: Verification Item의 고유 식별자.
- `verificationId`: Item이 속한 Restore Verification 식별자.
- `tableName`: 검증한 table 이름.
- `existsInRestoredDb`: table이 복원 DB에 존재하는지의 여부.
- `rowCount`: 복원된 table에서 확인한 row 수.
- `status`: `VERIFIED`, `MISSING`, `COUNT_FAILED`, `SKIPPED` 중 하나인 table 검증 결과.
- `message`: table 검증 결과의 상세 설명.
- `createdAt`: table 검증 결과가 생성된 시각.

행위:

- `static verified(...)`: table 존재와 row count 확인에 성공한 `VERIFIED` Item을 생성한다.
- `static missing(...)`: 복원 DB에 table이 없는 `MISSING` Item을 생성한다.
- `static countFailed(...)`: table은 있지만 row count 확인에 실패한 `COUNT_FAILED` Item을 생성한다.
- `static skipped(...)`: 검증을 수행하지 않은 `SKIPPED` Item을 생성한다.

- 규칙: 모든 Item은 결과별 named factory로 생성하며 생성 후 변경하지 않는다.

### 5.7 Audit

#### AuditLog

- 의미: 이미 일어난 운영 행위의 불변 기록.
- 현재 구현: JPA Entity, 독립 Repository에 기존 기록을 바꾸지 않고 새 기록만 추가하는 방식(append-only)으로 저장.
- 도메인 분류: **Aggregate Root / Entity**. 각 Audit Log는 다른 개체의 생명주기에 포함되지 않고 독립적으로 생성·조회되는 불변 기록이다.

속성:

- `id`: Audit Log의 고유 식별자.
- `actor`: 운영 행위를 요청하거나 수행한 사용자·시스템.
- `action`: 수행한 운영 행위의 종류.
- `resourceType`: 행위의 대상이 된 자원 종류.
- `resourceId`: 행위의 대상이 된 자원 식별자.
- `result`: 행위 결과의 문자열 분류.
- `message`: 행위와 결과에 대한 상세 설명.
- `createdAt`: Audit Log가 생성된 시각.

행위:

- `static create(...)`: 운영 행위의 주체·대상·결과를 가진 불변 Audit Log를 생성한다.

- 보완 필요: action/resource/result가 문자열이어서 용어 표준을 코드로 강제하지 못한다.

## 6. 현재 모델의 구조적 문제

1. **풍부한 모델과 데이터 모델의 혼재**: Job·Task·Agent·Apply는 상태 행위를 가지지만 Snapshot·Drift·HealthResult는 생성과 집계 규칙을 Service에 의존한다.
2. **ID만으로 연결된 엔티티**: 모든 연관이 `Long` ID이며 aggregate boundary가 코드에 명확히 드러나지 않는다.
3. **시각 생성의 직접 의존**: 도메인이 `LocalDateTime.now()`를 직접 호출해 테스트와 timezone 일관성이 약하다.
4. **중복·모호한 타입**: `database.domain.DatabaseStatus`(관리 상태)와 `health.domain.DatabaseStatus`(연결 상태), `DatabaseEngine`과 `ConfigurationEngineType`이 따로 존재한다.
5. **JSON payload의 약한 계약**: Job/Task의 parameter와 result가 String으로 저장되어 type별 계약이 DTO와 executor에 흩어져 있다.
6. **불변식 공백**: 생성자 validation, 상태 전이, 집계 count, enum과 행위 사이에 빈틈이 있다.
7. **문서 노후화**: 최상위 개요와 architecture 문서가 현재 구현 범위를 반영하지 못한다.

## 7. 점진적 개선 원칙과 순서

### 7.1 원칙

- 한 번에 전체 엔티티를 재설계하지 않고, 하나의 유스케이스와 aggregate씩 문서·코드·테스트를 같이 정렬한다.
- 표현 간결화와 도메인 모델 풍부화를 구분한다. Lombok은 boilerplate를 줄이지만 불변식을 만들지는 않는다.
- Entity에는 `@Data`, public setter, 무분별한 `@Builder` 사용을 피한다. `@Getter`, `@NoArgsConstructor(access = PROTECTED)` 정도를 기본으로 하고 생성과 변경은 의미 있는 메서드로 제한한다.
- 기존 API·DB schema 호환성을 유지하며 작은 단계로 변경한다.

### 7.2 권장 순서

1. 이 문서와 `용어 정리.md`의 미확정 항목을 합의한다.
2. `ManagedDatabase` Aggregate부터 생성·수정 불변식, DB 접속 인증 정보 경계와 용어를 정렬한다.
3. `OperationJob`/`OperationTask`의 상태 전이 표를 코드와 테스트에 고정하고 취소·재시도·실행권 규칙을 보완한다.
4. Configuration Profile을 aggregate root로 보고 parameter 규칙을 안으로 옮긴다.
5. Snapshot·Drift·Apply의 집계 무결성과 value type을 정렬한다.
6. Backup Verification의 Job/Task 연결과 cleanup 성공 정책을 확정한다.
7. 각 단계에서 도메인 테스트를 상태 전이·불변식 중심으로 재구성하고, application·adapter·API 테스트와 분리한다.
8. Lombok을 도입해 수동 getter·JPA 기본 생성자를 점진적으로 제거한다.

## 8. 확정이 필요한 질문

- 공식 한국어를 `관리 DB`로 할지 `DB 인스턴스`로 할지.
- Inventory의 활성 상태와 Health의 건강 상태 이름을 어떻게 분리할지.
- DB engine enum을 공유할지, 컨텍스트별로 변환할지.
- Job 취소의 허용 상태와 Agent Task 취소를 지원할지.
- Profile은 Active 상태에서 parameter 변경을 허용할지.
- Apply의 partial success를 운영적 성공으로 볼지, 실패로 볼지.
- 복원은 성공했지만 cleanup이 실패한 백업을 전체 성공으로 볼지.
- `LocalDateTime`을 유지할지 `Instant` 또는 offset 포함 시각으로 통일할지.
